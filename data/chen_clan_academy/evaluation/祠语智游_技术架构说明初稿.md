## 一、总体架构

“祠语智游”采用“确定性导游控制层 + 受约束生成表达层”的双层架构，以 Python 和 LangGraph 构建有状态、多节点的智能导游工作流。系统没有让大模型独立决定路线、事实和状态，而是把人工导游的服务过程拆分为语义理解、游客画像、路线规划、空间导航、点位讲解、知识问答、角色表达、状态提交和游后服务等职责明确的模块。

确定性控制层掌握审核知识、场馆空间、路线顺序、游客位置、游览进度和已讲内容，是系统的权威事实来源；生成表达层根据游客选择的中性清晰、儿童友好、专业讲解、古风书生、静听等风格，对已经确定的内容进行语言组织。候选正文只有通过事实、路线、安全、角色和时长校验后，才允许在限定范围内展示；否则自动回退到原有安全正文。

建议采用五层横向架构：

```text
交互与可观测层

                         ↓

                         ↓
```

## 二、Agent 工作流与状态管理

项目以 LangGraph StateGraph 编排多轮流程。游客输入首先经过语义归一与确定性仲裁，再依据当前会话阶段进入画像收集、路线选择、到达、讲解、问答、完成、跳过、重规划或游后服务节点。相比单一 Prompt，状态图能够处理“到了”“完成本点”“再讲详细一点”“不用了”等高度依赖上下文的表达，并保证中断后仍可恢复当前旅程。

核心状态包括：

| 状态对象 | 主要内容 | 作用 |
|---|---|---|
| VisitorProfile | 语言、时间、兴趣、讲解深度、角色偏好 | 生成个性化路线与表达策略 |
| TourState | 当前点、已访问点、剩余点、路线状态 | 保证路线连续推进 |
| QAContext | 问题对象、证据范围、追问许可 | 支撑当前点问答与连续追问 |
| Coverage | 已介绍工艺、对象、主题和提交记录 | 避免重复讲解并支撑游后总结 |
| Proposal | 重规划候选及确认状态 | 防止未经确认直接修改路线 |

路线或 Coverage 等正式状态采用受控写入、原子提交与幂等约束。角色模型不能修改 TourState、VisitorProfile、路线、Proposal 或 StopProgram，也不能执行工具调用。

### 【图 2：核心 Agent 流程图——必须制作】

```text
游客输入
  ↓
语义归一与意图仲裁
  ├─ 游前：画像收集 → 路线规划 → 路线开场
  ├─ 游中：定位/到达 → 点位讲解 → 下一站导航
  ├─ 问答：受控检索 → 基础答案 → 角色问答 Shadow → 追问
  └─ 游后：总结 → 称号与祝福 → 周边推荐
                         ↓
              状态提交、Coverage 与审计
```

制图时在“点位讲解”旁增加角色 ContentPlan、候选生成、质量门和回退支路，体现智能表达与业务控制分离。

## 三、知识、检索与空间计算

知识层以场馆审核资料、结构化知识卡、路线数据和服务信息为基础，覆盖建筑工艺、装饰对象、术语，以及开放时间、交通、票务和现场服务等内容。系统采用混合检索：BM25 负责对象名和专有术语的精确匹配，BGE 稠密向量负责自然语言语义召回，再通过 RRF 融合结果，并可选用重排序器提升相关性；Chroma 用于向量存储。问答只能在当前审核证据边界内组织答案，并把证据范围写入 QAContext，支持“再讲详细一点”等连续追问。

空间层将馆内点位和合法通路表示为审核空间图，使用 NetworkX 计算可达路径和预计步行时间。路线规划综合游客时间、兴趣、讲解深度、点位价值和步行成本；重规划先产生 Proposal，获得游客确认后才更新正式路线。馆外周边推荐与馆内路线隔离，商户不会写入场馆 `route_stop_ids`。

### 【图 3：知识与空间协同图——建议制作】

左侧画“审核资料→知识卡→BM25/BGE→RRF→受控问答”；右侧画“点位→空间拓扑→NetworkX→路线/导航”；中间通过 VisitorProfile、TourState 和 QAContext 连接，最终输出讲解、问答和路径提示。

## 四、角色表达与可信质量门

中性清晰讲解是项目的核心内容主干，角色化能力在其上提供差异化表达。系统先由确定性模块生成 ContentPlan，明确必须覆盖的事实 ID、内容预算、安全要求和禁止声明；DeepSeek API 仅根据该计划生成表达候选。角色候选采用闭合 Schema，并经过以下质量门：

- **事实一致性：** 使用的事实 ID 必须属于当前计划，不得新增或遗漏必需事实；
- **路线一致性：** 不得改动点位、顺序、时间和路径；
- **公共输出安全：** 拦截内部 ID、文件路径、URL、来源编号和状态字段；
- **角色一致性：** 儿童模式保持易懂，专业模式不擅增术语，静听模式不新增互动任务，古风模式不虚构史实；
- **预算一致性：** 正文与角色连接语不得超过讲解时长预算；
- **状态零写入：** 生成与校验节点不得修改正式业务状态。

系统支持 Shadow 与受限 Active 两类发布模式。Shadow 只记录候选与校验，不改变游客正文；受限 Active 仅在白名单角色、场景、路线和点位中接管输出。发生模型超时、非法 JSON、事实漂移、预算超限或内部字段泄漏时，系统自动回退旧版完整正文，并确保 Coverage 只提交一次。

```text
审核事实与状态
      ↓
ContentPlan → 角色候选 → Schema/事实/安全/预算校验
                              ├─ 通过且命中白名单 → Active 展示
                              └─ Shadow 或失败 → 旧链正文
                                            ↓
                                Coverage 单次提交与审计
```

## 五、技术选型与当前实现范围

| 类别 | 技术或模块 | 当前用途 |
|---|---|---|
| Agent 编排 | Python、LangGraph | 多轮状态图、条件路由与节点编排 |
| 生成模型 | DeepSeek API | 受约束的角色化表达候选 |
| 检索 | BM25、BGE、RRF、可选重排序 | 审核知识混合检索 |
| 数据存储 | Markdown/JSON 知识卡、Chroma | 结构化资料与向量索引 |
| 空间计算 | NetworkX | 合法路径与步行时间计算 |
| 状态系统 | VisitorProfile、TourState、QAContext、Coverage | 画像、进度、追问和知识覆盖管理 |
| 可观测性 | LangSmith Studio | 节点、候选、校验、耗时、接管与回退审计 |

当前原型已经连通游前画像与路线规划、路线开场、馆内导航、点位讲解、任意阶段问答与追问、完成/跳过/受控重规划、游后总结、称号祝福和周边推荐。18 种风格已完成自动化 Shadow 验证；比赛演示版本对中性、儿童、专业及古风书生的部分场景开放受限 Active，角色问答保持 Shadow。最近记录的本地工程回归为 `1118/1118` 通过，该结果用于说明模块间未发现测试回归，不代表外部试点或商业落地数据。

项目目前属于可运行原型 Demo，尚未形成真实场馆试点、正式运营用户或商业订单。后续接入新场馆时，主要替换知识卡、路线模板、空间拓扑和服务信息，Agent 编排、状态模型、质量门和审计能力可以复用。

## 六、技术价值总结

本项目的技术价值不在于增加一个能回答景点问题的聊天窗口，而在于把人工导游的完整服务逻辑工程化：系统既能理解游客和安排路线，也能记住位置、进度与已讲内容，在现场持续讲解、答疑和引路，并以多角色表达提升沉浸感。确定性控制与生成式表达分层，使个性化体验不会以牺牲路线正确性、知识边界和状态一致性为代价；模块化知识、空间和工作流设计，也为从陈家祠扩展到更多文化场馆提供了明确路径。
