## 一、项目摘要

“祠语智游”是一名贯穿游前、游中与游后的 AI 文化导游，而不是固定语音包或单轮问答机器人。项目以广州陈家祠为首个场景，将人工导游“了解游客、规划路线、沿途引导、到点讲解、随时答疑、掌握进度、完成收束”的服务逻辑，拆解为可运行、可追踪、可复用的智能流程。

游客只需说明语言、可用时间、兴趣方向、讲解深度和表达偏好，系统即可从审核路线、点位和空间关系中生成适合当前游客的游览方案。进入场馆后，系统持续维护当前位置、已参观内容、剩余行程和已讲知识，完成路线开场、到站讲解、下一站引导、完成或跳过、受控重规划等操作。游客可在任意环节询问建筑、工艺、装饰、术语及当前点位，也可查询开放时间、交通、票务和现场服务，并围绕上一轮答案继续追问。

中性清晰讲解是项目的核心主干，保证内容完整、准确、易懂；古风书生是角色化创新的代表，使路线规划、开场和点位讲解形成连续的人设体验；儿童友好、专业讲解、静听等表达策略则服务不同人群。游览结束后，系统依据真实参观记录生成总结、专属称号和祝福，并衔接经审核的周边餐饮、饮品与休息推荐，让导游服务从“带游客看完”延伸到“帮助游客理解、记住并自然结束旅程”。

项目采用“确定性决策层＋生成式表达层”的双层架构：事实、路线、位置、状态与安全规则由确定性系统控制，生成模型负责如何组织和表达；候选内容需通过结构、事实 ID、时长预算、角色一致性和公开输出校验，异常时自动回退稳定正文。当前已形成可演示的完整旅程原型，并完成角色化路线、开场和点位讲解的有限 Active 闭环。

## 二、项目定位与问题洞察

### 2.1 对标对象：人工导游

优秀的人工导游不仅“知道景点资料”，还会先了解游客有多少时间、对什么感兴趣、希望听到什么深度；进入场馆后，会根据游客位置和参观进度安排讲解，回答临时问题，提醒下一站，必要时调整节奏，并在旅程结束时完成总结和告别。

但人工导游服务受人员数量、服务时段、预约条件、语言能力和高峰客流限制，难以覆盖所有自由行游客。传统数字导览虽然扩大了内容供给，却通常仍停留在固定路线、扫码播放或独立问答：路线、讲解、答疑、引路和游后服务彼此割裂，无法形成持续理解游客的完整体验。

“祠语智游”要解决的核心问题，是如何把人工导游的连续服务能力转化为可规模化的数字能力，同时避免通用生成模型在文化事实、空间路线和状态控制上的不确定性。

### 2.2 现有体验的四类断点

1. **路线与游客不匹配。** 同一条固定路线难以同时服务 30 分钟游客、深度文化爱好者、亲子家庭和研学群体。
2. **讲解与现场脱节。** 固定音频不知道游客现在在哪里、已经听过什么，也无法根据时间与兴趣调整重点。
3. **问答与旅程脱节。** 通用问答可以回答一句，却常常不知道“这里”“这个”“再详细一点”具体指向什么，也无法保证回答不改变路线进度。
4. **服务在离馆前中断。** 多数导览在最后一个点位结束，缺少依据实际参观内容生成的总结、记忆点和后续服务衔接。

### 2.3 目标用户

- **自由行游客：** 希望无需预约即可获得清晰路线、重点讲解和即时答疑；
- **亲子家庭：** 需要更直观、短句化且不降低安全要求的解释方式；
- **研学与学生群体：** 需要观察、比较、分析等有任务感但不虚构结论的讲解；
- **文化深度爱好者：** 需要更完整的工艺、建筑、装饰和历史语境；
- **文化场馆管理者：** 希望扩展自助导览服务，并将知识、路线和服务信息沉淀为可维护的数字资产。

## 三、解决方案总体设计

### 3.1 完整旅程闭环

项目围绕游客真实参观流程建立九个连续环节：

1. **欢迎与需求识别：** 识别语言、游览模式、可用时间、兴趣、讲解深度与角色偏好；
2. **个性路线规划：** 从审核路线和合法空间关系中选择适合方案，输出路线主题、停留顺序、预计时间和第一站；
3. **路线开场：** 介绍场馆、路线主题、参观节奏、首站重点和必要提示；
4. **空间引导：** 给出当前位置、下一站、合法路径和预计步行时间；
5. **到站讲解：** 围绕当前建筑、工艺和装饰对象组织结构化讲解；
6. **任意环节问答：** 回答当前点位、历史、工艺、术语、开放时间、交通和票务问题；
7. **连续追问：** 理解“这个是什么”“再讲详细一点”等上下文指代，保持上一问范围；
8. **进度控制：** 支持到达、完成、跳过、下一站和受控重规划；
9. **游后服务：** 依据实际参观记录生成总结、称号、祝福及经审核的周边推荐。

### 3.2 产品体验原则

- **像导游一样连续，而不是每轮重新开始；**
- **先有权威内容，再做个性表达；**
- **路线、问答和讲解共享同一旅程状态；**
- **角色有辨识度，但不能替代事实；**
- **模型失败时，游客仍能完成游览。**

### 【图 3：游客旅程泳道图——必须制作】

建议分为三条泳道：游客、智能导游、场馆可信底座。

```text
游客：提出需求 → 确认路线 → 到达 → 听讲/提问 → 完成 → 离馆
导游：建画像 → 选路线 → 开场 → 引路 → 讲解/答疑 → 更新进度 → 总结推荐
底座：审核知识 → 路线模板 → 空间拓扑 → ContentPlan → 校验回退 → Coverage
```

## 四、核心功能与应用场景

### 4.1 个性化路线规划

系统综合游客可用时间、兴趣方向、讲解深度、语言和当前位置，从已经审核的路线模板与点位目录中选择可行路线，而不是让模型自由编造路线。路线说明包括：

- 路线主题与适合人群；
- 总时长和各点建议停留时间；
- 点位顺序及兴趣覆盖；
- 讲解、观察、互动与步行时间构成；
- 第一站、下一步动作和现场不确定性提示。

当游客在游览中提出调整需求时，系统先形成重规划建议，确认后再变更路线，避免一句自然语言直接改写游览状态。

### 4.2 路线开场与空间引路

路线开场不是一段固定欢迎词，而是连接路线规划与现场游览的“导游开场”：说明本次路线主题、总时长、停留顺序、第一站观察重点和参观节奏。空间引导则基于审核空间拓扑给出合法路径、方向与预计步行时间，并明确现场开放、客流和临时管控以场馆安排为准。

### 4.3 点位讲解：中性清晰为核心，角色表达为增量

点位讲解先由结构化内容计划确定“讲什么”，包括：

- 当前空间或主题背景；
- 已审核工艺与对象；
- 对象所在构件及观察位置；
- 必须包含和不得声称的内容；
- 讲解预算、下一步提示和安全边界。

中性清晰讲解承担最核心的稳定服务：完整、直观、容易理解。角色化能力在这一主干上改变称呼、句式、节奏和组织方式。例如古风书生以克制的古雅连接语形成沉浸感，儿童友好使用更短句和直观解释，专业讲解提高术语组织密度，静听模式减少提问和互动打断。

### 4.4 任意环节问答与连续追问

问答不是游览之外的独立聊天窗口，而是嵌入旅程中的能力。游客可以询问：

- 当前点位的建筑、工艺、装饰对象和术语；
- 某个对象的造型、位置、工艺特点和审核实例；
- 不同工艺或对象之间的比较；
- “这里”“这个”“刚才说的”所指内容；
- 开放时间、票务、交通、饮食与现场服务规则；
- “再讲详细一点”等基于上一轮答案的追问。

系统先由既有受控知识链生成答案，再将答案转为问答内容计划，角色层仅调整表达，不重新检索或扩充事实。问答不会自动推进路线，也不会改变当前位置。

### 4.5 进度、记忆与 Coverage

系统持续记录当前点、已访问点、剩余点和已讲事实。Coverage 使导游知道游客真正听过哪些内容：既能减少重复讲解，也能为最后的参观总结和称号生成提供依据。状态写入采用幂等与原子提交，避免同一事实因 Active 正文或回退正文被重复记录。

### 4.6 打卡建议与安全提示

项目将拍照建议设计为场景服务，而不是开放式姿势生成。建议明确合适背景、构图方向、现场可见性和客流限制，并禁止攀坐、倚靠、触摸文物、阻塞通道或进入非开放区域。

### 4.7 游览总结、专属称号与周边推荐

结束时，系统根据实际参观点位、听过的主题、提出的问题和显式兴趣生成：

- 本次游览内容总结；
- 趣味纪念称号与祝福；
- 未完成内容或离场建议；
- 经审核的周边餐饮、面食、奶茶、咖啡、甜品或休息候选。

周边推荐与馆内路线严格分离：推荐不会把商户写入场馆路线，也不会改变 TourState；游客拒绝推荐时只做简短确认。

## 五、技术架构与实现路径

### 5.1 总体技术架构

项目采用 Python 与 LangGraph 构建状态化 Agent 图，将复杂导游服务拆分为语义、画像、路线、状态、空间、知识、讲解、角色表达、校验和游后服务等节点。系统不是让一个大模型端到端决定所有行为，而是按照不同责任分层协作。

#### 交互与应用层

- LangSmith Studio 作为当前原型交互与可观测界面；
- 后续可接入 H5、小程序、场馆公众号或自助导览终端；
- 当前以文字交互为主，语音能力列入后续路线图。

#### Agent 编排层

- `semantic_normalization`：语义归一与意图仲裁；
- `visitor_onboarding/profile_collection`：游客画像；
- `direct_route/route proposal`：路线选择与建议；
- `tour_opening/stop_guidance/navigation`：开场、讲解和引路；
- `tour_qa/qa_follow_up_detail`：受控问答与追问；
- `visit_summary/post_visit`：总结、称号、祝福和推荐；
- Active、Shadow、fallback 等受控分支。

#### 确定性控制层

- VisitorProfile：语言、时长、兴趣、深度、角色偏好；
- TourState：当前点、已访问点、剩余点、路线进度；
- 路线模板、点位目录与空间拓扑；
- 审核事实、来源、时效和公开边界；
- Coverage 与原子状态提交；
- 安全规则和受控澄清。

#### 生成式表达层

- DeepSeek API 负责受约束的角色表达候选；
- ContentPlan 固定事实集合、内容结构、预算与交互权限；
- 模型仅排列审核事实占位符并生成有限连接语；
- 不允许模型生成路线、状态补丁、内部 ID 或工具调用。

#### 知识与检索层

- Markdown 与结构化知识卡保存场馆、工艺、建筑、对象和服务信息；
- BM25 关键词检索与 BGE 稠密向量检索并行；
- RRF 融合，可选 reranker 重排；
- Chroma 支持向量存储；
- 回答保留来源、审核状态与时效约束。

#### 空间与路线层

- 审核路线模板约束可选游线；
- NetworkX 在审核空间图上计算合法最短路径与步行时间；
- 当前位置、目标点和重规划均通过确定性逻辑更新。

#### 可观测与质量层

- LangSmith 展示节点路径、输入输出和运行耗时；
- 记录 ContentPlan、角色候选、校验、Active/Shadow 判定与回退；
- 自动化测试覆盖路由、状态、知识、讲解、角色、预算和安全输出。

### 【图 5：系统总体架构图——必须制作】

建议五层结构，从上到下：

```text
游客与交互入口
        ↓
LangGraph Agent 编排层
        ↓
确定性控制层 ←→ 生成式表达层
        ↓               ↓
知识检索层         内容计划与质量门
        ↘               ↙
     状态提交、审计与 LangSmith 可观测
```

图中必须明确两条箭头：

1. 确定性层向生成层提供“审核事实与结构计划”；
2. 生成候选只有通过质量门才可有限 Active，否则回到旧链正文。

### 5.2 为什么采用 LangGraph 状态图

真实导游任务包含长期状态和多种控制分支：同一句“到了”“完成”“不用了”“再讲详细一点”，在不同阶段可能对应不同动作。LangGraph 使每个节点职责明确，状态变化可追踪，并允许在路线、问答、讲解和总结之间建立稳定连接。与单 Prompt Agent 相比，它更适合处理“多轮、可中断、可恢复、状态敏感”的现场服务。

### 5.3 关键状态模型

| 状态对象 | 记录内容 | 作用 |
|---|---|---|
| VisitorProfile | 语言、时长、兴趣、深度、角色偏好 | 个性化路线与表达 |
| TourState | 路线、当前点、已访问、剩余点、状态 | 保证旅程连续和正确推进 |
| QAContext | 当前问答对象、上一问范围、可追问信息 | 支持指代和连续追问 |
| Coverage | 已介绍工艺、对象、主题及提交记录 | 减少重复并支持总结 |
| Proposal | 待确认的重规划或路线变更 | 防止自然语言直接改状态 |

建议以状态机形式表现：

```text

```

## 六、知识问答与可信内容体系

### 6.1 知识资产组织

项目将原始场馆资料转化为可计算资产，而不是简单把长文档放入向量库。知识内容按场馆基本信息、历史建筑、工艺主题、装饰对象、空间位置、开放服务、票务交通等类别组织，并保留来源、审核状态、更新时间与公开边界。

点位知识卡将“工艺—对象—构件位置—观察方式—来源”关联起来，使系统既能回答“灰塑是什么”，也能回答“这个独角狮在哪里看”“月台的石雕有什么实例”。

### 6.2 混合检索

系统同时使用：

- BM25：适合专有名词、对象名和精确术语；
- BGE 向量检索：适合自然语言表达和语义近似问题；
- RRF：融合两路排序，兼顾关键词与语义召回；
- 条件重排：在必要时提高结果相关性；
- 场景过滤：根据当前点位、问题类型和审核状态缩小证据范围。

### 6.3 受控问答路径

```text
游客问题
→ 意图与对象识别
→ 当前点位/显式点位范围确定
→ 审核知识检索
→ 受控答案生成
→ QA ContentPlan
→ 角色候选与校验（当前 Shadow）
→ 游客看到权威答案
```

角色层不会重新检索，也不会把内部来源编号、文件名、URL 或原始 chunk 暴露给游客。

### 【图 7：知识问答架构图——建议制作】

左侧画知识来源，中间画结构化处理与混合检索，右侧画受控答案、角色表达和输出校验。特别标出“角色表达不改变证据集合”。

## 七、路线规划与空间约束

### 7.1 路线不是大模型自由规划

文化场馆路线涉及开放区域、合法通道、空间方向、步行时间和游览顺序。项目将路线决策建立在审核路线模板、点位目录和空间拓扑上，模型不能创建不存在的点位或路径。

### 7.2 路线选择逻辑

输入因素包括：

- 明确可用时间；
- 游客兴趣与希望覆盖的工艺；
- 标准或深度讲解需求；
- 当前是否已经在游览中；
- 已访问点和剩余点；
- 角色表达偏好不参与路线事实决策。

输出包括路线 ID（仅内部使用）、点位顺序、停留时间、步行时间、兴趣覆盖、第一站和结束建议。

### 7.3 空间引路与受控重规划

NetworkX 根据审核空间图计算当前位置到目标点的合法路径。重规划先生成 proposal，只有确认后才改变路线；周边商户推荐与馆内路线隔离，不能被加入 `route_stop_ids`。

### 【图 8：路线与空间图——必须制作】

建议使用陈家祠简化平面拓扑示意，而非真实测绘图。节点标注“入口、前院中部、月台、前东庭”等审核点位，边标注可通行方向和步行时间。旁边增加路线选择输入输出框。

## 八、角色化导游与质量门

### 8.1 从“角色 Prompt”升级为“受控角色表达”

项目支持中性清晰、儿童友好、亲子共游、研学观察、专业讲解、静听模式、古风书生、粤派讲古等 18 种表达策略。创新重点不是角色数量，而是角色能否在路线、开场、讲解和问答中保持连续，同时不改变事实、路线和状态。

### 8.2 ContentPlan

在模型生成前，系统先构建结构化内容计划，定义：

- 场景类型与角色模式；
- 必须使用的审核事实 ID；
- 内容目标和必需段落；
- 可选观察任务；
- 安全要求与不得声称内容；
- 内容时长预算；
- 资料不足或候选非法时的回退方式。

### 8.3 角色候选质量门

候选需依次通过：

1. Schema 与版本校验；
2. 事实 ID 完整性与边界一致性；
3. 路线节点、顺序和时长一致性；
4. 角色风格一致性；
5. 内容预算校验；
6. 内部字段与公开输出安全校验；
7. 特定角色硬边界，如静听模式不得新增互动。

超时、非法 JSON、事实漂移、预算超限或内部字段泄漏时，候选失败关闭，游客继续看到完整旧版正文。

### 8.4 Shadow 与有限 Active

- **Shadow：** 生成和审计角色候选，但游客仍看到旧链正文；
- **Active：** 仅在配置开关、场景与风格白名单、候选校验全部通过时展示角色正文；
- **Fallback：** 任一条件失败即回退旧链，且 Coverage 只提交一次。

比赛版已形成以下有限 Active：

- 古风书生：路线规划、路线开场、两个审核充分点位讲解；
- 中性清晰与儿童友好：白名单点位讲解；
- 角色问答：当前保持 Shadow，不直接替换权威答案。

### 【图 9：角色生成—校验—回退流程图——必须制作】

```text
旧链事实/路线/安全正文
→ ContentPlan
→ 角色候选
→ Schema / 事实 / 路线 / 预算 / 角色 / 泄漏校验
   ├─ 通过＋命中白名单 → Active 展示 → Coverage 单次提交
   └─ Shadow 或失败     → 旧链正文 → Coverage 单次提交
```

## 九、技术创新点与差异化优势

### 9.1 将人工导游服务工程化

项目不以单一问答准确率定义智能导游，而是把需求理解、路线、开场、引路、讲解、问答、进度和游后服务连成一条状态化工作流，使系统具备“陪游客完成一次旅程”的能力。

### 9.2 确定性决策与生成式表达双引擎

确定性系统负责去哪、讲什么、当前状态和安全规则；生成模型负责怎么讲。该分工既保留中性清晰讲解的稳定性，也让古风书生等角色具备真正可展示的沉浸感。

### 9.3 同一事实，多人群表达

通过 ContentPlan 和事实 ID，同一组审核知识可按儿童、研学、专业、静听、古风等策略重新组织，而不需要为每个角色重建知识库。它将角色能力从一次性文案升级为可复用的表达层。

### 9.4 旅程状态与知识 Coverage 联动

系统不仅知道游客在哪里，还知道已经讲过什么。路线进度与 Coverage 共同支撑避免重复、连续追问、个性总结、称号与祝福，使“记住游客的旅程”成为产品体验的一部分。

### 9.5 可审计、可回退、可灰度

每次候选都能看到来源计划、角色、事实集合、校验结果、Active/Shadow 判定和状态写入。模型异常不会让整条导览失效，系统可按风格和场景逐步开放，而不是一次性把所有能力交给模型。

### 9.6 从单馆原型到场馆接入方法

项目将知识、空间、路线、角色和安全规则建设为配置资产。陈家祠首个场景验证的价值，不只是完成一个景点 Demo，更是形成文化场馆数字导游的接入框架。

## 十一、与“AI+旅游休闲”命题的契合度

本项目直接覆盖命题提出的智能行程规划、AI 虚拟导游、沉浸式体验创新和智慧旅游线上服务。

1. **智能行程规划：** 根据时间、兴趣和讲解深度，在审核路线中生成可执行方案；
2. **AI 虚拟导游：** 具备开场、引路、讲解、问答、进度管理和收束能力；
3. **沉浸式体验创新：** 以古风书生等连续角色表达，让岭南建筑与非遗内容更具情境感；
4. **线上服务延伸：** 问答覆盖开放时间、票务、交通与周边服务，未来可接入小程序和场馆线上入口；
5. **广州文化表达：** 以陈家祠和岭南建筑装饰工艺为首个场景，形成具有本地文化辨识度的 AI 导览样板。

项目将“智能”落实为路线因人而变、讲解随程而变、问题随时可问、角色连续一致和游后留下记忆；将“有温度”落实为适合不同人群的表达、不中断的陪伴和个性化总结祝福。

## 十五、风险控制与可信运行

安全不是项目唯一卖点，但它是文化导游能够真正运行的基础。

| 风险 | 控制方式 |
|---|---|
| 文化事实虚构 | 审核知识、事实 ID、不得声称列表、候选事实边界校验 |
| 路线与空间漂移 | 审核路线模板、空间拓扑、NetworkX 合法路径 |
| 模型直接改状态 | 状态写入只由确定性节点执行，角色候选 `state_writes=[]` |
| 角色掩盖内容 | 中性清晰主链、必需事实、角色一致性和预算限制 |
| 儿童/拍照/闯关风险 | 专项硬边界与危险表达拦截 |
| 模型超时或非法输出 | fail-closed，自动回退完整旧版正文 |
| 重复讲解或重复提交 | Coverage 与幂等提交 |
| 内部信息泄漏 | 文件名、URL、来源 ID、节点 ID 和原始 chunk 棔测 |

## 十九、结语

“祠语智游”希望补足的，不是场馆资料的数量，而是数字服务中“像一名导游一样陪伴”的能力。它既能用中性清晰的方式把文化讲明白，也能用古风书生等角色让旅程更有情境；既能规划和引路，也能在游客产生好奇的那一刻回答问题；既记得走到了哪里，也记得已经听过什么，并在离开时为这次参观留下总结和祝福。

项目以陈家祠为首个文化场景，验证了一条务实的技术路线：让确定性系统守住事实、空间和状态，让生成式模型释放表达和体验创新。它不是以“模型无所不能”为前提，而是通过结构化知识、状态化 Agent、内容计划、质量门和自动回退，把 AI 的创造力放在真正适合的位置。由此形成的，不只是一个可演示的导览原型，也是一套可向博物馆、古建景区和非遗场馆复制的智能导游方法。
