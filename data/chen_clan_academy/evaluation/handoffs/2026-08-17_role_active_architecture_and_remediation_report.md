# 18 风格 Active 架构现状与改动建议报告

日期：2026-08-17  
面向：项目开发与测试成员  
依据：当前代码审阅、`2026-08-17_18_style_active_manual_test_log.md`、兄弟搭子游客端截图。  
范围：说明当前 Active 实现实际做了什么、为什么风格呈现死板，以及下一轮应如何修复与验收。

## 1. 先说结论

当前“18 风格 Active”并不等于“18 个风格都由 LLM 自由、自然地写出完整导览”。

以本轮 `buddy_guide`（兄弟搭子）为例，截图中：

```text
路线：咱们抓重点，按安排往下走。
点位：咱们先抓眼前这个重点。
```

确实是兄弟搭子对应的风格组件，并非本轮证据中的“闺蜜唠嗑选错”。问题是这些组件只是在大段确定性旧链正文前后插入一两句，无法形成稳定、自然、有陪伴感的角色表达。

因此：

1. 当前配置可能已经让候选获得 Active 资格；
2. 但路线类正文当前不是 LLM 自由生成，风格差异天然很小；
3. 点位讲解中，LLM 主要受限于事实令牌和已审核组件，`buddy_guide` 等多数风格没有自然话语试点能力；
4. 仅继续调整 prompt，无法解决路线死板、长段排版和服务尾部混排问题；需要改“内容计划—渲染—校验”的表达结构。

在完成下列 P0/P1 修复前，不建议继续把其他风格的文字质量判为通过或失败；否则会重复记录同一底层缺陷。

## 1.1 2026-08-17 新增真实测试结果：最后五种非粤语风格

### 已确认：兄弟搭子点位讲解是真实 Active，不是 fallback

同一到站 turn 的 `narration_commit.active_role_narration_audit` 显示：

```text
fallback_used = false
legacy_message_preserved = false
same_public_message = false
model_called = true
reason_codes = []
role_consistent = true
same_fact_boundary = true
public_message_safe = true
service_tail_passed = true
```

这证明游客端的“兄弟搭子”点位正文为真实角色候选发布：模型参与、旧链正文未被原样保留、未发生 fallback，且事实/安全/服务尾部校验均通过。它依然死板，因而问题应定性为**真实 Active 输出的体验质量不合格**，而不是配置未生效。

### 测试者体验结论：最后五种非粤语风格均缺少自然 AI 感

测试范围为：

```text
bestie_chat（闺蜜唠嗑）
buddy_guide（兄弟搭子）
exploration_game（探秘闯关）
photo_guide（打卡出片）
hostel_scholar（青旅学者）
```

测试者反馈：五种输出整体相似，看不出 LLM 根据风格、路线、当前对象进行自然组织的痕迹；开头引领固定、点位正文长且同质、角色差异不足。该反馈应作为本轮体验验收的**不通过结论**，而不是继续要求测试者逐个补测相同问题。

### 探秘闯关路线截图的可观察证据

截图显示已在页面选择“探秘闯关”，但路线正文仅增加：

```text
这一段的线索已经排好，慢慢找。
```

其余正文仍为通用路线资料单，包含：

```text
详细讲解将围绕工艺、构件、题材和可核验证据展开
```

该句在每个站点重复，且“可核验证据”属于内部工作流语言，不应出现于游客端。路线的站点、时长、兴趣、提示和下一站信息未被组织为探秘过程；因此该风格不是“探索式智能导游”，而是“通用路线 + 固定探秘前缀”。

### 体验问题汇总

| 问题 | 截图/Trace 结论 | 用户影响 |
|---|---|---|
| 风格只体现在一条前缀 | 兄弟搭子、探秘闯关均有直接证据 | 五种人格几乎不可区分 |
| LLM 自然表达不足 | 点位虽 `model_called=true`，但大多数语句仍由固定组件/旧事实拼接 | 像规则型 App，不像智能导游 |
| 路线不使用 LLM 生成表达 | 当前路线路径设计上无模型调用 | 开场引领和路线叙事必然死板 |
| 长块排版 | 点位讲解、服务尾部、导航、拍摄内容被压进长正文 | 难读，风格节奏完全丢失 |
| 内部语言泄漏 | “可核验证据”、审核关联、项目编辑、未核验等 | 破坏游客体验与可信度 |

## 1.2 本轮产品决策建议

用户目标应调整为：**从“安全的角色前缀包装”升级为“事实受控、表达自然的狭义 AI 导游”。**

这不等于让模型自由生成文化知识或路线，而是扩大它在以下范围内的表达自由：

```text
允许模型：角色开场、观察顺序、事实之间的自然承接、情绪节奏、比喻、收束。
禁止模型：站点、时长、方向、审核事实、传说细节、对象位置、安全要求、Coverage 和状态写入。
```

模型生成的每段表达必须映射到明确槽位，并经服务端检查：无新增事实、无后台词、无重复口头禅、无危险互动、满足角色合同。不可通过时回退到“自然的确定性角色模板”，而非原始资料卡。

## 2. 当前架构：真实运行方式

### 2.1 风格选择

```text
中文显示名/别名
→ profile_dialogue 的 STYLE_ALIASES / EXPLICIT_STYLE_PHRASES
→ VisitorProfile.explanation_style
→ role_mode_confirmation
→ selected_style_id
```

代码中已定义 `bestie_chat=闺蜜唠嗑`、`buddy_guide=兄弟搭子` 等别名，但人工日志已发现多个显示名在选择入口未被接受、需要“跳过”才能继续。该问题属于入口解析或 onboarding 状态传递问题，不能仅以“别名表中已有定义”视为修复。

### 2.2 路线规划、开场、引路、结束语

当前路径为：

```text
确定性路线/开场/引路/总结旧链正文
→ route_role_narration_shadow.build_route_role_text_candidate
→ 固定风格前缀 + 完整旧链正文
→ 精确保留旧链事实的校验
→ Active 接管或 legacy 保留
```

关键事实：`build_route_role_text_candidate` 明确不调用模型。它只拼接固定短前缀，例如：

```text
bestie_chat：这段行程有几个细节，咱们边走边看。
buddy_guide：咱们抓重点，按安排往下走。
```

这保证路线、时长、安全提示不会漂移，但也决定了路线主体仍是同一份成人化、密集的旧链正文。当前“路线类 Active”本质上是固定包装接管，不是 LLM 根据游客和审核内容进行自然角色化讲述。

### 2.3 点位讲解

当前路径为：

```text
审核证据与 StopProgram
→ narration_rendering 生成 fact_units
→ narration_content_plan
→ role_narration_generation
→ narration_validation
→ narration_commit 或 deterministic_narration_fallback
```

模型受到严格约束：它不能自行扩展审核事实，主要输出事实令牌；服务端再将事实与 YAML 风格组件拼接。这样能保护事实边界，但会产生两个问题：

- 大多数风格的开头/中段/结尾来自固定组件，容易像“模板串接”；
- 当前自然话语试点仅覆盖 `child`、`ancient_scholar`、`dominant_ceo` 的 compact 模式，`bestie_chat`、`buddy_guide`、`photo_guide` 等不会得到 LLM 生成的自然连接语。

### 2.4 当前排版与服务尾部

点位校验当前倾向把成功角色候选视为连续正文，换行会触发 `layout_not_continuous` 类限制。结果是工艺、对象、完成提示、下一站导航、拍摄建议容易挤成一整段。

截图中出现的：

```text
审核关联 / 可结合现场标识观察 / 项目编辑整理 / 未核验
```

并非角色“更有特色”的内容，而是确定性事实/服务文本泄漏到游客端。它们需要在事实呈现和服务尾部层修复，不能靠风格 prompt 清洗。

## 3. 已确认的产品问题

| 编号 | 问题 | 类型 | 影响 |
|---|---|---|---|
| P0-1 | 路线类 Active 仅固定前缀，角色差异过弱 | 架构限制 | 闺蜜、搭子等人格无法成立 |
| P0-2 | 点位正文将多个事实、服务尾部、导航、拍摄内容压成超长块 | 渲染/校验限制 | 可读性差，风格节奏被淹没 |
| P0-2A | 点位节点缺少语义缩进与逻辑层级：工艺、对象、传说、观察、完成、下一站被平铺或混排 | 内容计划与段落渲染缺口 | 游客不知道当前讲解对象、转场原因和下一步属于哪一层 |
| P0-3 | 多数风格无自然中段表达，只能使用 YAML 模板组件 | 表达能力缺口 | 组件化痕迹强、语句僵硬 |
| P0-4 | 游客正文出现审核/未核验/项目编辑等后台语言 | 事实呈现与服务尾部泄漏 | 不应对游客展示 |
| P1-1 | 中文显示名选择在人工测试中未稳定生效 | 入口解析/状态问题 | 无法确认用户是否显式选中目标风格 |
| P1-2 | 月台首讲没有兑现路线承诺的对象与工艺内容 | 当前点计划或回退问题 | 路线与讲解不一致 |
| P1-3 | “再讲详细一点”与“完成本点”的顺序影响后续点首讲、信息密度和 Coverage | 状态机问题 | 结果不可复现，详情合同失效 |
| P1-4 | 主动拍摄建议与正文/内部说明混排；结束总结的完成数与覆盖数矛盾 | 服务尾部/Coverage 问题 | 合适点位的推荐应保留，但不能打断讲解或泄漏内部口吻 |

## 4. 推荐改动方向

### P0：先建立“可读、可区分”的统一表达结构

不要直接允许 LLM 重写路线、方向、时间或审核事实。推荐改为：

```text
不可变事实单元
+
受控角色表达槽位
+
独立服务单元
→ 段落化游客正文
```

每个场景最少分为：

```text
1. 风格开场（1 个短段）
2. 当前点/路线的核心事实（1～3 个短段）
3. 风格化承接或观察视角（1 个短段）
4. 完成提示 / 下一站导航 / 拍摄建议（独立服务段，仅在应出现时出现）
```

校验器不应再以“整篇完全无换行”作为成功条件。应允许受控的段落边界，同时继续禁止 Markdown 标题、内部字段、空段堆叠和任意列表格式。

### P0-节点排版：按讲解逻辑建立可读层级

当前截图的问题不只是缩进消失，而是节点结构没有游客可理解的逻辑：

```text
工艺定义
→ 对象身份
→ 长传说
→ 观察位置
→ 第二个对象
→ 完成提示
→ 下一站导航
→ 拍摄建议
```

这些内容被连续拼接，缺少“为什么现在讲这一项、与当前点有什么关系”的承接。建议建立不可见的节点层级，并映射为固定段落结构：

```text
当前点的观察目标（短段）
→ 工艺或空间背景（短段）
→ 对象一：身份 + 一个最值得看的细节（短段）
→ 对象二：仅在与当前点相关时承接（短段）
→ 已审核传说：独立短段，明确使用“传说里/人们说”
→ 本点收束（短段）
→ 完成/下一站/拍摄：独立服务区，不与讲解正文混排
```

要求：

- 每一段只承担一个节点目的；
- 只有当前 `stop_id` 的对象可进入该点主讲；
- 无关对象、历史详情和未触发的服务单元不进入首讲；
- 转场由风格化表达解释，而不是“对象这块接着看”等无指代模板句；
- 前端使用段落间距、短段和受控视觉层级，不使用资料卡标题或整篇首行缩进伪造层次。

### P0-A：路线类从“固定前缀”升级为受控角色化路线呈现

新增 `RoutePresentationPlan`，将原路线正文拆为不可变单元：

```text
route_summary
duration
stop_sequence
per_stop_focus
safety_notice
first_navigation
```

然后为每个风格提供：

```text
route_opening
route_transition
route_focus_bridge
route_closing
```

第一阶段仍由服务端确定性渲染，避免路线事实漂移；不再只在全文前加一条固定前缀。这样即使不用 LLM，也能让兄弟搭子、闺蜜唠嗑等在节奏、称呼、关注方式和收束上有连续差异。

第二阶段才允许 LLM 为每个槽位输出“无事实连接语 JSON”。模型只能生成开场、承接、收束，不能生成站点、时间、方向、事实或安全内容；服务端验证后再组合。

### P0-B：点位讲解扩展自然话语，但事实仍由服务端锁定

将现有 `child / ancient_scholar / dominant_ceo` 的自然话语试点扩展为通用能力，而不是立即开放自由改写。

推荐模型输出：

```json
{
  "opening": "无事实的角色开场",
  "bridges": ["每个事实单元之间的无事实承接"],
  "closing": "无事实收束"
}
```

服务端必须继续负责：

- 事实单元的选择、顺序、次数；
- 专名、数字、工艺名、传说限定语、否定关系；
- 当前点 `stop_id` 与对象边界；
- 连接语长度、去重、互动限制、后台词过滤；
- 失败时的风格化确定性 fallback。

针对兄弟搭子，目标不是重复“抓重点”，而是体现“可靠同行、直接说清观察顺序、不过度命令”的连续语气。针对闺蜜唠嗑，目标是“轻松分享发现、不过度私密或网络化”。

### P1：先修统一底层缺陷，再恢复多风格人工测试

1. **风格显示名映射**：统一支持显示名、显示名+“风格”、`style_id`；修复 onboarding 后用 18 风格参数化测试验证 `VisitorProfile.explanation_style` 与 `selected_style_id` 一致。
2. **月台首讲**：把月台设为固定回归样本，首次到达必须命中当前 `stop_id` 的审核对象和路线承诺内容，不能退化为泛化木雕句。
3. **详情不污染状态**：详情路径不得写 Coverage、完成状态、下一站内容选择或角色续讲状态；使用“直接完成 / 详情后完成 / 多次详情后完成”三条 Thread 做状态快照对比。
4. **服务尾部隔离**：允许在已审核且合适的点位主动推荐拍摄；但拍摄建议必须单独成段、不得抢占首讲主线，移除“项目编辑整理”“未核验”等内部表达；结束总结分别陈述“完成点位数”和“成功讲解 Coverage”，不得互相矛盾。

### P1-A：把“风格是否真的有差异”变成可验收合同

不能再以“出现了一句角色口头禅”作为通过标准。每个风格的路线、开场、点位至少应具备以下可观察差异：

| 检查维度 | 合格标准 |
|---|---|
| 角色连续性 | 开场、事实承接、收束至少三处均能识别同一角色，不是只在首句出现一次。 |
| 表达差异 | 同一份路线事实下，`bestie_chat`、`buddy_guide`、`exploration_game`、`photo_guide`、`hostel_scholar` 的连接语、观察顺序和收束不能完全相同。 |
| 叙事组织 | 路线要把站点组织成该风格可理解的过程；点位要有“看什么 → 发现什么 → 为什么值得看”的节奏。 |
| 排版 | 路线、点位、服务尾部为受控短段，不能是一整块长文；无需资料卡标题。 |
| 节点逻辑 | 每段明确属于当前点目标、工艺背景、对象观察、传说、收束或服务区；段落顺序与当前 `stop_id` 一致。 |
| 内部语言 | 游客端不得出现审核、证据、关联、项目编辑、未核验、节点、资料卡等词。 |
| 事实与安全 | 站点、时间、方向、专名、传说限定语和安全提示准确；模型不得新增知识。 |

建议为每个场景增加两类测试：

1. **结构化自动测试**：验证槽位、事实边界、段落数、禁止词、服务尾部时机和不同 style 组件/表达不完全相同；
2. **五风格体验回归**：固定同一条 30 分钟路线，分别比较五种路线规划、首站、月台、详情、下一站和结束语，保存最终正文快照，不再要求测试者先看节点。

LangSmith 只用于确认“确实 Active / 确实模型参与 / 是否 fallback”，不再替代游客端文字质量验收。

## 5. 如何确认某条样本真的 Active，且模型是否参与

游客正文不能单独证明 Active，因为固定组件和 fallback 都可能看起来带有一点风格。

在同一 Thread、同一到站 turn 中，仅需查看以下最小字段：

| 场景 | 必看节点/记录 | 真实 Active 的判定 |
|---|---|---|
| 路线规划/开场/引路/结束语 | `route_role_narration_evaluations` | `validation_status=accepted` 且 `active_takeover=true`；此类场景当前 `model_called=false` 是设计现状，不表示失败。 |
| 点位讲解 | `role_narration_generation` → `narration_validation` → `narration_commit` | generation 的 `style_id` 正确；最终 `narration_commit.commit_decision=role_candidate_published`、`active_takeover=true`、`fallback_used=false`。 |
| 问答/追问 | `qa_role_narration_generation` → `qa_role_narration_validation` → `qa_role_narration_commit` | 最终 commit 的 `active_takeover=true` 且未走 legacy QA fallback。 |

对点位/QA：`model_called=true` 表示模型参与了受限候选生成；它不表示模型可读取原始知识库或自由撰写全部正文。模型只处理经过 ContentPlan 筛选后的事实令牌/连接语范围。

## 6. 建议验收顺序

1. 暂停“剩余风格文字质量”验收，先修 P0-1～P0-4；
2. 用古风书生做回归基线，确保路线、事实、Coverage 和 fallback 不变；
3. 用兄弟搭子与闺蜜唠嗑作为“强口语人格”验收样本，确认不是只换一句前缀；
4. 用儿童友好验证受控故事感与适龄表达；

## 8. 2026-08-17 追加的统一整改决策：18 种风格改为受控知识下的 LLM 完整讲解

### 8.1 古风书生也不再是合格基线

新增截图表明，`ancient_scholar`（古风书生）虽然使用了“诸位、且看、再察其工”等表面风格词，但导览开场和当前点讲解仍然是：

```text
少量古风前缀/连接句
+
成人资料句、审核关联、构件位置辨认、完整长传说、服务尾部与拍摄建议的连续拼接
```

因此古风书生不是可复制的成熟全链路标杆，也不能再作为其他 17 种风格只需“补齐前缀”的参考实现。它和兄弟搭子、探秘闯关面对的是同一架构问题：**风格词由模板提供，核心讲解并未真正由角色化 LLM 组织。**

本轮统一验收结论应改为：18 种风格（包括 `ancient_scholar`）目前均不得以“已具备自然 AI 导游体验”标记通过；仅可标记为“已接入 Active 候选链路”或“待体验整改”。

### 8.2 目标架构：不是拼接，而是“角色 Prompt + 受控知识 + LLM 完整成文”

团队需要停止把下面这种模式继续扩展到 18 种风格：

```text
固定角色前缀
+ 审核事实原句逐条拼接
+ 固定服务尾部
```

统一改为：

```text
统一导游 System Prompt（安全、事实、服务边界）
+ 场景 Prompt（路线规划 / 开场 / 当前点 / 问答 / 引路 / 收束）
+ 风格 Prompt（18 种角色的语气、关系感、节奏、禁忌与示例）
+ 已选审核知识包（带事实 ID、对象/站点边界、传说标识、优先级）
+ 当前会话状态（时间、兴趣、已讲内容、当前 stop、允许的服务动作）
→ LLM 直接生成面向游客的完整自然讲解草稿
→ 服务端事实、结构、安全、服务时机校验
→ 发布；失败才回退到同风格的确定性可读稿
```

这里的“自由发挥”应理解为：LLM 可以自行决定叙事顺序、开场方式、段落节奏、观察切入点、比喻、轻度拟人、情绪和自然承接；**不能**自行增加知识、路线、数字、方向、传说细节、对象关系或服务动作。

也就是说，LLM 不再只填 `opening/bridges/closing` 三个无事实槽位，而是对经过筛选的知识包进行完整的角色化成文。事实受控靠输入知识结构和后验验证实现，不能再靠把整段成人资料原样拼回去实现。

### 8.3 Prompt 分层要求

每次模型调用必须带上以下四层输入；不要把角色风格只写进 YAML 短句后再拼接：

1. **统一角色导游 Prompt**：说明这是陪同游客实地导览；要求先回应当前目标，再讲最有价值的线索；一段只讲一个意思；不展示后台流程；不进行考试式连续提问；不诱导触摸、攀爬、摆拍或阻塞通道。
2. **场景 Prompt**：明确本轮是路线规划、开场、到站讲解、问答、引路或结束；明确本轮允许哪些服务信息，未触发的拍摄/导航/完成提示不得混入。
3. **风格 Prompt（18 份角色合同）**：除称谓外，必须定义关系感、句子节奏、常用叙事动作、观察方式、情绪浓度、禁用语气、2～3 条正反例。角色 Prompt 不是硬编码口头禅清单，必须允许同一角色每轮自然变化并避免重复。
4. **知识与状态 Prompt**：仅传入本场景可讲的审核事实、传说标记、专名/数字锁定项、对象与 `stop_id` 边界、已覆盖事实及会话状态。模型必须在这些材料内组织，不能引用未提供信息。

建议要求模型返回结构化草稿，而不是从模板拼文本，例如：

```json
{
  "paragraphs": [
    {"purpose": "opening", "text": "...", "fact_ids": []},
    {"purpose": "focus", "text": "...", "fact_ids": ["..."]},
    {"purpose": "object_detail", "text": "...", "fact_ids": ["..."]},
    {"purpose": "legend", "text": "...", "fact_ids": ["..."], "legend_marked": true},
    {"purpose": "closing", "text": "...", "fact_ids": []}
  ]
}
```

服务信息应由独立受控单元在模型正文后组合，或作为受限 `service` 段输出；不得再无条件拼入正文。

### 8.4 校验必须从“逐字保留”转为“可追溯的语义一致”

为实现完整成文，必须同步替换/收紧当前导致拼接化的验证思路：

- 取消“审核原句必须几乎原样出现”“全文不得换行”这类把体验锁死的要求；
- 保留并加强每段 `fact_ids`、当前 `stop_id`、必讲/可省略事实、Coverage 写入的追踪；
- 锁定专名、数字、工艺名、对象身份、否定关系、方向和已审核传说的不确定性标记；
- 对每个事实做语义蕴含/方向检查：不得扩充事件、年代、人物、用途、空间关系或传说细节；
- 过滤后台词（审核、证据、关联、节点、项目编辑、未核验、资料卡等）、危险动作和重复口头禅；
- 校验段落目的顺序、长度和服务时机；允许自然短段，不允许大段资料卡；
- 校验失败时，回退到**同一角色、同一场景、同一事实包**生成的确定性段落稿，而不是旧的成人资料串。

这是一次架构级调整；如果只在 YAML 增加更多口头禅、放松 `repeated_role_expression` 或继续扩展固定前缀，无法达到目标。

### 8.5 所有场景一起改，不再只修点位

以下场景都必须使用同一套“Prompt 分层 + 知识包 + LLM 完整成文 + 校验”的表达框架：

| 场景 | 体验目标 | 严禁退回的做法 |
|---|---|---|
| 路线规划 | 以角色方式解释为什么这样走、每站有什么期待 | 通用路线表 + 一句风格前缀 |
| 导览开场 | 建立角色关系与本次游览的期待 | 角色句后粘贴百科式总介绍 |
| 当前点讲解 | 围绕一个观察目标带出工艺、对象、故事 | 原始事实逐条拼接成资料长段 |
| 问答/追问 | 真正回应游客问题，并按角色调整深浅与比喻 | 固定答案前后加称谓 |
| 引路 | 简短、自然、只说当下需要的方向/安全信息 | 将下一站全文、拍摄建议混进讲解 |
| 结束/改线 | 回顾真实已完成内容，并自然给出后续选择 | Coverage 内部状态直接翻译成游客文案 |

### 8.6 新验收门槛与最小测试集

在迁移后，18 风格不得再只检查 `active_takeover=true`。每个风格至少跑一条固定 30 分钟路线，并覆盖：路线规划、开场、首站、月台、一次详情追问、下一站引路、结束。

每条样本同时满足：

1. LangSmith：真实 Active 发布、模型被调用、无 legacy/fallback；
2. 游客端：三段以上自然短段，段落逻辑清楚，不是资料卡/一大段；
3. 风格：相同事实下与至少两个其他风格明显不同，且全程至少三处可识别角色关系与叙事节奏；
4. 知识：无新增事实；传说有“传说里/人们说”等边界；专名、数字和对象身份正确；
5. 服务：主动拍摄建议只出现在已审核且合适的点位，并独立成段、无内部话语；完成、详情、引路和结束不污染彼此状态；
6. UX：不含后台术语，首点和月台均有与路线承诺一致的讲解。

为节省人工时间，建议先自动生成 18 × 固定场景的文本快照，再由测试者只做“同风格是否有角色感、是否自然、是否可读”的快速验收；节点只用于排查失败样本，不作为每次人工测试前置步骤。

### 8.7 建议实施顺序

1. 抽出统一 `RoleNarrationPrompt`、`SceneNarrationPrompt`、`KnowledgePack` 和结构化 `RoleNarrationDraft`；
2. 先把路线规划、开场、当前点讲解迁移到完整成文链路，并修复段落逻辑；
3. 将古风书生、兄弟搭子、闺蜜唠嗑、探秘闯关设为第一批对照风格，验证“文雅叙事 / 同行口语 / 亲密分享 / 探索推进”确实不同；
4. 接入其余 14 种风格；所有角色使用相同安全与知识校验，不再各自维护一套拼接规则；
5. 再迁移 QA、引路、结束与改线，最后修复月台、详情状态、拍摄时机和 Coverage 回归。

**请以本节作为后续实现的优先级说明。** 当前报告前文的“先保持路线确定性、仅让 LLM 写无事实连接语”仅可作为临时过渡方案；最终目标以本节的“受控知识下的 LLM 完整成文”为准。
