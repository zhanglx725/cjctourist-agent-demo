# 陈家祠智能导游：完整产品功能开发总路线图

## 1. 文档定位

本文是比赛资料冻结后，项目转向完整产品开发的统一执行方案。它整合以下四种视角：

- 游客视角：是否好用、有趣、愿意持续使用和分享；
- 场馆视角：是否可信、可管理、可运营、能降低服务成本；
- 投资视角：是否可复制、可收费、可形成数据与技术壁垒；
- 创新项目评审视角：是否解决真实问题、具有技术创新、社会价值和产业化证据。

比赛材料已冻结为历史快照。本文只描述冻结后的产品开发，不回写或覆盖比赛历史事实。

## 3. 最终产品目标

产品最终应从“陈家祠单场馆导游 Agent”演进为“可服务多场馆的可信智能导览平台”。

游客端目标可归纳为：

```text
一眼识物：知道游客正在看什么
一问即懂：用审核知识回答当前问题
一路相伴：路线、讲解、问答和引路保持连续
一游成册：把真实参观内容沉淀为数字记忆
```

场馆端目标可归纳为：

```text
内容可审核
路线可配置
版本可回滚
服务可观测
运营可分析
场馆可复制
成本可控制
系统可降级
```

## 4. 不可破坏的架构原则

1. Workflow 决定路线、状态和正式业务动作。
2. 审核知识决定可使用的事实边界。
3. Agent 只负责理解、组织和表达候选。
4. Validator 决定候选是否可以发布。
5. 模型不得直接写 TourState、VisitorProfile、路线、Coverage 或 Proposal。
6. 定位、视觉识别和语音识别结果都只是候选，必须经过确定性确认。
7. 模型失败时，基础导览、路线、安全信息和审核正文仍然可用。
8. 游客可见正文不得泄漏 source ID、文件路径、节点名、Trace 或内部 reason code。
9. Coverage 只记录真正向游客发布的审核事实。
10. 未知配置、未知对象、证据不足和状态冲突一律失败关闭。

## 7. 阶段 1：产品级能力配置与场景校验重构

### 目标

将比赛专用白名单演进为产品级能力策略，并彻底分离点位、问答、引路和结束语的校验合同。

### 使用技术

- Python `dataclass` / `TypedDict`；
- YAML 或严格 JSON 配置；
- LangGraph 条件边；
- 环境变量兼容层；
- 确定性哈希分流；
- unittest 参数化矩阵。

### 具体步骤

1. 新增 `ProductCapabilityPolicy`、`ProductScenePolicy` 和 `ProductStylePolicy`。
2. 配置按 `capability + scene + style` 控制 mode、灰度比例、校验等级、回退策略和 kill switch。
3. 保留旧环境变量读取，仅作为兼容输入。
4. 未知风格、场景、模式或不完整配置全部关闭。
5. 同一 Thread 固定 rollout 决策，避免轮次间漂移。
6. 建立场景校验入口：
   - `validate_stop_guidance_role_narration`；
   - `validate_qa_role_narration`；
   - `validate_navigation_role_narration`；
   - `validate_closing_role_narration`；
   - `validate_replan_presentation`。
7. 抽取共享 Schema、事实、内部字段、安全和预算校验。
8. 保留各场景自己的专属约束，禁止再次让点位组件校验误伤 QA。
9. 增加配置解析、Thread 稳定性、kill switch 和兼容性测试。

### 验收标准

- 核心判断不再直接依赖比赛命名的白名单；
- 五类场景校验相互隔离；
- 默认关闭和失败关闭有效；
- 完整回归全部通过。

## 8. 阶段 2：长讲解预算自适应与分轮输出

### 目标

解决长点位包含多个事实单元时角色 scaffold 超预算只能整体回退的问题，同时不删除必须事实或污染 Coverage。

### 使用技术

- 预算预估器；
- 动态规划或确定性贪心分组；
- LangGraph continuation 状态；
- 原子 Coverage 提交；
- Pydantic/dataclass 严格合同。

### 具体步骤

1. 新增 `NarrationBudgetDecision`，记录事实预算、角色连接语预算、选中与延后单元。
2. 在调用模型前执行可行性预检。
3. 定义四级策略：
   - 完整角色 scaffold；
   - 紧凑 scaffold；
   - 按 `fact_unit` 分轮；
   - 确定性旧链回退。
4. 为风格组件增加 `full` 与 `compact` 审核短句，不允许运行时自由压缩事实。
5. 新增 `NarrationContinuation`，保存待讲事实单元、已发布事实和 freshness 快照。
6. 支持“继续、下一部分、先讲工艺、跳过剩余内容”。
7. 离开点位、路线变化或角色冲突时使旧 continuation 失效。
8. Coverage 只提交当轮实际发布事实。
9. 防止重复“继续”造成重复提交。
10. 为 1、3、12 个事实和不同预算建立测试矩阵。

### 验收标准

- 长讲解可以完整、紧凑或分轮完成；
- 事实原字、顺序和对象绑定不变；
- 延后事实不提前进入 Coverage；
- 任何失败仍能安全回退；
- TourState 和路线不被角色层修改。

## 9. 阶段 3：角色化问答 Active

### 目标

将 `tour_qa` 和 `qa_follow_up_detail` 从 Shadow 推进为受控产品 Active。

### 使用技术

- QA 专用 ContentPlan；
- LangGraph Active commit/fallback 分支；
- 严格 JSON Schema；
- 事实字符串保持与范围继承；
- 线程上下文审计。

### 具体步骤

1. 为角色增加 QA 专用 opening、direct answer、follow-up、uncertainty 和 closing 组件。
2. QA 只接收已经审核和公开安全过滤后的答案，不重新读取原始 chunk。
3. 追问继承原问题主题、事实范围、语言与角色。
4. “再详细点”不能开放无限检索或生成新故事。
5. 新增 `qa_role_narration_commit`，只有 accepted 且策略允许时替换游客正文。
6. Shadow 或失败时保留原审核答案。
7. listen_only 不主动提问或布置任务。
8. 测试儿童、专业、古风、静听和中性角色。
9. 覆盖定义、对象故事、比较、研究、位置、证据不足和多轮追问。
10. 验证 QA 永不写 TourState、路线、画像或 Coverage。

### 验收标准

- QA Active 可按策略灰度开放；
- 问答事实边界与旧审核答案一致；
- 追问不扩大范围；
- 模型失败时答案仍可用；
- QA 专属回归全部通过。

## 10. 阶段 4：引路、结束语与重规划说明 Active

### 目标

完成完整旅程的角色表达接管，但路线和状态继续由 Workflow 掌握。

### 使用技术

- 审核空间图 NetworkX；
- NavigationPresentationPlan；
- ClosingPresentationPlan；
- ReplanPresentationPlan；
- LangGraph proposal/confirmation；
- 路径与状态差异验证器。

### 具体步骤

1. 引路计划固定起点、终点、审核路径、方向、步行时间和免责声明。
2. 校验角色正文未新增左转、右转、捷径或非开放区域。
3. 结束语只使用实际 TourState、Coverage、称号和审核服务信息。
4. 不得总结未参观的点位或未讲过的工艺。
5. listen_only 结束语不主动提出问题。
6. 重规划角色层只解释已经生成或应用的 Proposal。
7. 未确认 Proposal 不得应用。
8. 位置或路线变化后旧 Proposal 和旧表达候选失效。
9. 为正常路径、走错、未知位置、跳过、结束和取消建立端到端测试。

### 验收标准

- 规划、开场、点位、问答、引路和结束语形成完整角色链；
- 路线事实逐项一致；
- 重规划保持确认和 freshness；
- fallback 不影响后续角色继承。

## 11. 阶段 5：全流程角色连续性与语音导游

### 目标

让角色成为真正的随行导游，并支持自然的语音播放、暂停、插话和续播。

### 使用技术

- 流式 TTS；
- ASR；
- Web Audio API 或移动端音频会话；
- 可中断播放队列；
- Thread/turn 状态机；
- 文本与音频内容哈希。

### 具体步骤

1. 统一角色选择、继承、显式切换和冲突澄清规则。
2. fallback 不清除角色；新 Thread 不继承旧角色。
3. TTS 只能朗读验证后的游客正文。
4. 支持暂停、继续、快进、语速和锁屏播放。
5. 游客插话时暂停音频，完成问答后从原段落恢复。
6. 离开点位或路线变化时停止旧音频。
7. 长讲解按分轮状态播放。
8. ASR 结果仍进入语义仲裁，不能直接触发状态写入。
9. 建立文本、音频一致性和中断恢复测试。

### 验收标准

- 完整旅程角色一致；
- 插话和续播自然；
- 音频不绕过验证；
- 语音误识别不造成状态误操作。

## 12. 阶段 6：定位与可视化地图

### 目标

解决“系统如何知道游客在哪里”，形成真实现场导览。

### 使用技术

- 二维码与深链接；
- NFC；
- 可选 BLE Beacon；
- GeoJSON/SVG 场馆地图；
- NetworkX 路径计算；
- 定位置信度融合。

### 具体步骤

1. 先实现成本最低的二维码点位确认。
2. 每个二维码只映射审核 stop ID，不包含游客敏感数据。
3. 增加 NFC 作为无相机入口。
4. 建立地图上的当前点、下一站、已完成、出口、洗手间和无障碍设施。
5. 定位结果先形成候选，再由 Workflow 校验是否允许到达。
6. 多来源冲突时请求游客确认。
7. 无定位时允许手动选择，不假装知道位置。
8. 后续再评估 BLE 或 Wi-Fi，避免早期绑定昂贵硬件。

### 验收标准

- 游客无需输入内部点位名称；
- 错误二维码或未知位置失败关闭；
- 地图进度与 TourState 一致；
- 定位不会绕过完成、跳过或重规划规则。

## 13. 阶段 7：AI 识物镜与历史场景叠影

### 目标

实现“一眼识物”，将视觉识别与审核对象知识安全连接。

### 使用技术

- 图像 embedding 与向量检索；
- 目标检测/视觉语言模型；
- 审核对象 canonical ID；
- 置信度校准；
- AR 标注或 WebXR；
- 图像隐私与临时存储。

### 具体步骤

1. 为审核展品建立训练/检索图片集和 canonical ID。
2. 先做候选检索，不直接输出唯一结论。
3. 综合当前点位、图像相似度和对象注册表排序。
4. 高置信度仍允许游客确认；低置信度必须展示候选。
5. 确认后调用现有对象级审核知识链。
6. 相机画面可高亮工艺、人物、动物和纹样观察区域。
7. 历史叠影必须标注“文献依据、专家复原、示意或不确定”。
8. 默认不长期保存游客照片；上传前明确授权。
9. 测试相似对象、同名对象、错误位置和无匹配对象。

### 验收标准

- 视觉结果不能绕过对象审核；
- 错误识别不会产生虚构讲解；
- 游客能够从识别结果直接进入讲解和路线状态；
- 图片处理符合隐私规则。

## 14. 阶段 8：创意游客体验

### 目标

形成愿意使用、收藏和分享的差异化体验。

### 功能一：数字游览护照

技术：TourState、Coverage、签名数字印章、分享卡片生成。

步骤：

1. 印章只绑定真实到达或实际讲解行为。
2. 生成已参观点位、关注工艺、数字称号和未完成区域。
3. 支持下次继续，但必须由游客授权保存。

### 功能二：文化关系图

技术：知识图谱、NetworkX、交互式 SVG/Canvas。

步骤：

1. 将游客实际听过的工艺、对象、人物和点位建立关系图。
2. 点击节点可回顾原讲解和位置。
3. 不显示未审核推断关系。

### 功能三：AI 摄影导演

技术：相机取景、光线方向估计、审核摄影点位、安全规则。

步骤：

1. 给出审核站位区域和构图建议。
2. 提供建筑对称、细节、亲子、古风等主题。
3. 禁止攀坐、触摸、堵塞通道或进入非开放区。
4. 拍摄后生成带审核说明的照片故事卡。

### 功能四：家庭协作与研学

技术：多人房间、WebSocket、任务状态、教师端报告。

步骤：

1. 家庭成员分工寻找动物、纹样和工艺。
2. 支持共同路线、集合点和任务进度。
3. 研学模式设置学习目标、观察记录和游后报告。
4. 未成年人数据最小化，不做羞辱性排名。

### 功能五：换一个视角再游一次

技术：Coverage 差集、主题路线推荐、授权记忆。

步骤：

1. 提供工艺、建筑、亲子、摄影、无障碍和二次到访路线。
2. 根据上次 Coverage 推荐未听内容。
3. 支持随时关闭或删除历史记录。

### 验收标准

- 创意功能与真实游览行为绑定；
- 能形成可分享但不泄露隐私的成果；
- 游戏化不损害文物安全和文化可信度。

## 15. 阶段 9：场馆 CMS 与运营后台

### 目标

让场馆人员不修改 Python 代码即可维护内容、路线和运营规则。

### 使用技术

- FastAPI/Django 后台服务；
- PostgreSQL；
- 对象存储；
- RBAC；
- 审核工作流；
- 版本化发布；
- React/Vue 管理后台。

### 具体步骤

1. 建立 Venue、Exhibition、Gallery、Stop、Object、Route、Evidence 和 SafetyRule 数据模型。
2. 实现草稿、审核、发布、下架和回滚。
3. 支持上传文档、图片、地图和展品表。
4. 自动抽取只能生成候选，必须人工审核后发布。
5. 实现路线编辑器和空间关系检查。
6. 建立 AI 回答审核中心，汇总无答案、低证据、回退和投诉问题。
7. 建立运营仪表盘：游客数、完成率、热门点位、问答成功率、fallback 率和语言分布。
8. 所有管理操作记录审计日志。

### 验收标准

- 场馆内容人员可以独立完成更新；
- 发布错误可以快速回滚；
- 数据变化可自动触发相关测试；
- 后台权限和审计完整。

## 16. 阶段 10：多场馆、多租户与快速接入

### 目标

证明产品可以从陈家祠复制到更多场馆，而不是项目制重写。

### 使用技术

- 多租户 PostgreSQL；
- 租户级对象存储与向量索引；
- 配置驱动 Graph；
- 数据导入 ETL；
- 自动生成回归集；
- 白标主题和域名。

### 具体步骤

1. 所有核心对象增加 `tenant_id` 与 `venue_id`。
2. 实现数据库、索引、文件和日志的租户隔离。
3. 建立场馆接入向导：上传、抽取、审核、点位、路线、测试、发布。
4. 支持独立品牌、语言、角色、模型和安全规则。
5. 接入第二个不同类型的小型场馆，禁止修改核心业务代码。
6. 记录接入时间、人力成本和需要人工修订的比例。
7. 将成功流程沉淀为模板。

### 验收标准

- 至少两个场馆运行在同一平台；
- 数据绝不跨场馆泄漏；
- 普通场馆目标接入周期控制在一至两周；
- 新场馆主要通过配置和审核数据接入。

## 18. 阶段 12：无障碍、多语言、隐私与安全

## 19. 阶段 13：生产部署与规模验证

### 目标

证明系统在真实游客量、真实网络和模型故障下仍然可靠。

### 使用技术

- OpenTelemetry；
- LangSmith；
- Prometheus/Grafana；
- Sentry；

## 20. 全阶段测试与质量门

每个阶段都必须通过以下四层验证：

1. 单元测试：解析器、计划器、校验器和状态转换。
2. 集成测试：LangGraph 节点与数据合同。
3. 完整回归：以 `1170/1170` 为起点，只能增加覆盖，不通过删除有效断言维持数字。
4. 人工验收：角色自然度、语音、地图、视觉识别和真实现场体验。

每次合并前必须满足：

```text
定向测试通过
完整回归通过
git diff --check 通过
无无关文件
无未解释的基线漂移
新增配置默认失败关闭
文档和状态矩阵已更新
```

关键产品指标包括：

- 游览启动率；
- 路线完成率；
- 平均使用时长；
- 问答成功率；
- fallback 率；
- 长讲解继续率；
- 语音播放完成率；
- 点位识别确认率；
- 游客满意度；
- 场馆内容更新时间；
- 新场馆接入周期；
- 单游客推理成本；
- 场馆续费率。

## 22. 最终完成定义

项目只有同时满足以下条件，才可以称为完整产品：

1. 游客能够通过语音、地图和识物完成真实现场游览。
2. 路线、事实、状态和安全始终由可信控制层掌握。
3. 角色覆盖规划、开场、讲解、问答、引路、重规划和结束语。
4. 长讲解可自适应或分轮，不丢失事实和 Coverage。
5. 场馆可以自行维护、审核、发布和回滚内容。
6. 新场馆无需重写核心代码即可接入。
7. 系统具备多租户、权限、计费、观测和故障降级。
8. 产品具备儿童、老人、残障和多语言服务能力。
9. 已获得真实游客、场馆和付费数据验证。
10. 所有关键能力均有自动测试、人工验收和可审计证据。

这条路线的核心不是继续增加表演性功能，而是把现有可信 Agent 架构扩展成同时具备游客体验、文化责任、场馆运营、商业闭环和跨场馆复制能力的文博智能导览平台。
