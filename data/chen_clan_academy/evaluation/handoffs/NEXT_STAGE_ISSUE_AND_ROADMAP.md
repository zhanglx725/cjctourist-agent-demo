**形成日期：** 2026-07-29

**检查基线：** `68b869ca457cd7dfb070625e4428a8471433a3d0`（`codex/e5-b-style-library`）
**性质：** 规划与交接材料；不改变现有冻结契约、公共 Agent 代码、空间图或知识卡原始数据。

## 1. 目标与判断原则

项目目标不是把陈家祠资料检索出来后逐句回答，而是在不虚构事实、不突破现场安全边界的前提下，根据游客**已明确的时间、游览模式、兴趣、当前审核点位和实际游览进度**，组织连续导览。

下一阶段不应以“再写 Prompt”或“改成 KAG”作为主线。当前已经具备混合 RAG、确定性路线、`TourState`、`VisitorProfile`、到达/确认事件和多类知识卡。真正缺口是：修复已验证的控制层问题、完成证据驱动讲解、明确产品模式，以及按审核条件调度卡片。

所有后续改动遵循以下边界：

- 路线、到达、跳过、完成、重规划继续只由确定性状态机修改；
- 陈家祠对象、位置、工艺、故事和保护规则必须由本地审核资料或可追溯来源支持；
- 大模型可以组织语言或回答非项目通用闲聊，不能自行决定“陈家祠事实不需要检索”；
- 无证据、空间映射冲突、运行资格缺失或现场条件未知时，必须失败关闭或说明资料不足；
- 每个“已修复”必须同时有自动化回归测试和 LangSmith 实际链路复测。

| 解决方案 | 复用已有确定性重规划/确认事件，将同一轮中解析到的审核 `node_id` 传入为重规划起点；不另建当前位置事实源、不猜测别名、不未经确认静默改写路线。 |
| 验收 | 不再把与新位置无关的旧 `pending_stop_id` 声称为下一站；确认后剩余路线从新点开始，保留已完成/跳过站点语义，并能继续到达讲解。 |

## 6. P2：经典 / 定制双模式产品协议

### P2-01 当前缺少明确的游览模式事实源

| 项目 | 内容 |
| --- | --- |
| 问题描述 | 当前已有时间、兴趣、详略和扩展画像字段，但没有“经典模式/定制模式”的统一产品协议。不能依靠聊天语气猜测游客想要哪种体验。 |
| 当前现状 | `VisitorProfile`、`GuidancePolicy`、扩展画像选择和 E5 风格素材已经存在；`tour_mode` 尚未成为冻结字段，也未接入路线/讲解策略。 |
| 期望状态 | 开始导览先获取可用时长，再由游客明确选择经典或定制模式。经典模式不主动追问偏好；定制模式只收集必要、可选且明确的偏好。 |
| 解决方案 | 先新增模式契约与状态归属设计，明确 `tour_mode` 属于 VisitorProfile、路线快照还是会话控制；随后才实现 UI/文本选择。不得删除现有 `detail_level`，因为它已参与路线预算与测试；可取消对游客强制询问，改为按模式应用透明默认。 |
| 验收 | 经典模式只靠时长生成代表性路线；定制模式只使用游客明确选择的偏好；两种模式均允许游客主动提问，但不擅自推断身份。 |

### P2-02 定制模式的偏好收集过多或含义重叠

| 项目 | 内容 |
| --- | --- |
| 问题描述 | 若依次询问时间、七类工艺、讲解深浅、人格风格、目的、同行人，容易变成冗长问卷；“简单/深入”又与知识水平、风格和时长部分重叠。 |
| 当前现状 | C5/C8 已有受众、知识水平、表达风格、互动方式的明确选择能力，但真实聊天默认仍是中性画像；没有面向双模式的最小收集流程。 |
| 期望状态 | 定制模式首版最多收集三项：工艺兴趣（多选）、讲解风格、可选的游览目的或同行情况；未填写项保持中性默认。 |
| 解决方案 | 使用多选而不是 127 种工艺组合；把“摄影、研学、亲子”等作为显式目的/同行提示，不从年龄或一句模糊表达推断。风格必须映射到 E5 允许的受控值。 |
| 验收 | 游客可跳过任一可选问题；系统不重复询问已回答字段，也不因“我们”“一起”自动判定家庭或儿童。 |

### P2-03 规划收集期间插入问题后的恢复策略未产品化

| 项目 | 内容 |
| --- | --- |
| 问题描述 | 游客在路线偏好收集过程中可能询问“三顾茅庐是什么意思”；系统应先回答，再恢复到真正缺失的规划字段，而不是卡死在线性问卷。 |
| 当前现状 | 现有 C2/A2 已优先保障问答与控制操作不直接破坏画像收集，但“双模式下的暂停、回答、恢复提示”尚无明确端到端产品验收。 |
| 期望状态 | 收集草稿保留；插入问答不覆盖已确认偏好；回答后只提示下一项必要字段，不强迫重复回答。 |
| 解决方案 | 在模式契约后定义 `profile_collection` 的暂停/恢复规则与验收案例；继续把 VisitorProfile 作为唯一画像事实源。 |
| 验收 | 时间已记录后插入事实问答，再回到收集时只询问模式或下一项缺失偏好。 |

## 7. P2：卡片调度与事件驱动导览

### P2-04 卡片存在，但没有受控的“到点调度”机制

| 项目 | 内容 |
| --- | --- |
| 问题描述 | 术语、比较、研究和打卡卡多数只能由游客直接提问触发，尚未根据当前审核点位、游览模式、兴趣和预算主动进入讲解。 |
| 当前现状 | D1-D6 已完成各类卡的注册、资格门控和问答接入；`StopProgram` 的相关卡片插槽仍未实际调度。E5 契约已规定讲解数据流，但 E5-A/C 尚未完成。 |
| 期望状态 | 到达审核节点后，基础对象事实必选；术语、比较、研究、打卡作为可选增强内容，并受模式、证据、预算、运行资格与现场边界共同限制。 |
| 解决方案 | E5 完成后新增确定性 `CardDispatcher`/调度规则，输入只能来自当前 `node_id`、StopProgram、GuidancePolicy、模式、已明确兴趣与资格注册表。输出为可审计的候选，最终讲解仍需 evidence。 |
| 验收 | 同一状态输入稳定选择相同卡片；无资格/无来源/无映射卡不进入游客文本；卡片调度不修改路线或 TourState。 |

### P2-05 比较卡、研究卡不能默认变成事实或强制插入

| 项目 | 内容 |
| --- | --- |
| 问题描述 | 希望导览有比较思路，但若每件木雕都自动做跨地区比较，会超时、越过证据边界，并把研究观点误说成定论。 |
| 当前现状 | D3/D4 已有研究归因和比较资格门控；八张比较卡目前为 `attributed_only / research_only`。 |
| 期望状态 | 比较卡仅在定制模式明确偏好、专业/研学策略、游客主动比较或本站确有合适证据时，以短小“可选深入说明”出现。研究卡始终以“相关研究指出”表述。 |
| 解决方案 | 在调度器中设定每站至多一个可选比较/研究扩展，并服从 StopProgram 时间预算；普通游客获得基础事实优先。 |
| 验收 | 普通经典路线不因卡片存在而超时；研究/比较内容显示归因、范围与限制。 |

### P2-06 打卡卡需要摄影明确意图和现场限制，不能变成默认推销

| 项目 | 内容 |
| --- | --- |
| 问题描述 | 希望到点提示拍照，但现有打卡卡只是项目编辑候选，不代表热门、馆方推荐、实时开放或可通行机位。 |
| 当前现状 | D5-B/D6 已有编辑候选门控、姿势安全边界和安全拒绝；平台观察永不进入游客内容。当前只在明确拍照请求时读取。 |
| 期望状态 | 仅在游客明确选择摄影目的/偏好，或主动询问拍照时，给出一条非接触、以现场标识和工作人员要求为准的可选提示。经典模式默认不主动插入拍照推荐。 |
| 解决方案 | 将 `photo_preference` 设计为显式、可选的会话偏好；调度器只使用已启用、当前节点关联且安全边界完整的候选。 |
| 验收 | 不选择摄影偏好的经典路线不出现拍照推销；摄影偏好下也不承诺光线、客流、开放或“热门”。 |

## 8. P3：位置事件与主动体验触发

### P3-01 从文本到达升级为可信位置事件

| 项目 | 内容 |
| --- | --- |
| 问题描述 | 真正的主动导览需要知道游客到了哪里；纯聊天文本无法可靠感知物理位置。 |
| 当前现状 | 已有文本 `arrive_at_stop` 和审核节点机制；空间别名冲突尚未关闭。没有 GPS、二维码、蓝牙或地图点击产品接口。 |
| 期望状态 | 先支持“游客点击地图点位/扫描二维码/明确确认到达”这类可信事件；只有确认事件才能触发本站主动讲解和候选提醒。 |
| 解决方案 | 在解决空间数据冲突后，定义 UI 中立的 `location_event` 输入契约；优先 QR 或地图点击，不在当前阶段加入不可靠 GPS 推断。 |
| 验收 | 事件带唯一审核 `node_id`，触发本站内容而不改变路线顺序；错误或未知点位失败关闭。 |

## 9. P3：知识分层与 Adaptive RAG 运行策略

### P3-02 不应让模型自行判定“知道就不检索”

| 项目 | 内容 |
| --- | --- |
| 问题描述 | 直接让 API 模型凭自信决定是否检索，容易对陈家祠事实、展品位置、故事细节或实时服务产生幻觉。 |
| 当前现状 | 项目已有本地混合 RAG、术语/研究/比较/拍照的确定性意图分流，但部分回答质量和路由顺序仍需修复。 |
| 期望状态 | 路线/状态走确定性代码；陈家祠事实和动态服务走本地证据；通用闲聊才可直接调用模型；证据不足时明确说明。 |
| 解决方案 | 在现有 `route_initial_request` 和 Tour QA 上逐步收紧分类与证据阈值，不引入第二套 RAG 或完整知识图谱。若未来要补通用文化故事，应建立可引用的背景资料层，而不是模型记忆层。 |
| 验收 | 任意陈家祠对象/位置/工艺回答可追溯；低相关检索不强答；通用闲聊不污染 TourState。 |

### P3-03 当前不需要把项目重构为完整 KAG

| 项目 | 内容 |
| --- | --- |
| 问题描述 | KAG/知识图谱听起来能解决“多跳关系”，但当前主要障碍是状态、调度、证据组织和空间数据一致性，而不是缺少图数据库。 |
| 当前现状 | 项目已有审核节点图、对象—点位映射、路线图和统一知识卡注册表，已具备后续结构化检索的基础。 |
| 期望状态 | 先用现有结构化数据完成可靠导览；只有出现稳定的多跳关系查询需求时，再评估图谱查询层。 |
| 解决方案 | 暂不引入 OpenSPG/图数据库等大规模重构。将“对象—工艺—点位—证据—卡片”关系保持在当前审核文件与适配器中，并通过调度器消费。 |
| 验收 | 不增加新基础设施也能完成路线、站点讲解、受控卡片调用与来源边界。 |

## 10. P4：暂缓项目

以下能力具有价值，但不应在 P1/P2 未完成前开工：

- GPS、蓝牙信标和视觉识别自动定位；
- 基于长期行为的个性化推荐；
- 跨会话长期游客画像与数据库持久化；
- 实时客流、开放时间、展览或票务同步；
- 多语言完整导览与语音前端；
- 自动生成新知识卡或自动写入空间关联。

它们都要求额外的授权、现场数据、隐私设计或人工审核，不能通过当前聊天/RAG 逻辑安全替代。

## 12. 每个任务的统一完成标准

一个问题只有同时满足以下条件才可从问题池关闭：

1. 有清晰的唯一事实源和文件所有权；
2. 不改变 TourState、VisitorProfile、路线和空间数据的既定边界；
3. 有针对原始用户表达的自动化回归测试；
4. 有 LangSmith 新线程与连续线程实测记录；
5. 无效证据、无效节点、审核不足和现场未知条件均安全降级；
6. 更新问题池状态、证据链接和受影响测试；
7. 经负责人确认后才提交、合并或推送公共分支。
