# Active 导览体验整改：下一步实施计划

日期：2026-08-17  
依据：`2026-08-17_role_active_architecture_and_remediation_report.md`、`2026-08-17_role_active_state_integrity_addendum.md`、当前工作区代码与 2026-08-17 游客端截图。

## 结论

两份交接文档提出的问题**尚未整体完成**，不能把当前游客端效果认定为整改完成。

已经存在但尚待统一回归的基础改动：

- 点位讲解校验已允许一个受控空行作为语义段落边界；不再因正常分段而拒绝候选。
- `role_discourse` 的完整自然叙事能力已接入点位链路，但必须同时开启两个迁移开关。
- 路线、开场、引路、结束具备“不可改写路线句 + 模型连接语”的候选协议；当前工作区还把 `route_opening` 加入该链路。
- 详情不污染 Coverage、结束总结统计 Active 首讲等状态修复，已在补充交接中记录，但仍明确标注为“待统一回归”。
- 当前未提交改动已把讲解正文与服务尾改为 `\n\n` 分隔。这是截图中长段混排的必要修复之一，但尚未验证前端渲染和全链路回归。

尚未解决或没有证据证明已解决的部分：

- 截图中的段落仍是长资料块，缺少“观察目标 → 工艺/对象 → 传说（如适用）→ 本点收束 → 独立服务区”的可读层级；仅增加空行不够。
- “兄弟搭子”“探秘闯关”等风格仍会呈现固定短前缀或固定组件痕迹；“抓重点”“接着看”“前往下一点”没有具体观察动作、关系感或场景推进。
- 路线开场和引路虽然有新版候选能力，但默认/未完整配置时仍会退到确定性前缀拼接。
- 部署说明曾遗漏第二个必需开关 `PRODUCT_ROLE_NATURAL_FULL_NARRATION_ENABLED=true`；本轮已补入 `README.md` 与 `demo/README_DEPLOY.md`，但实际部署 Secrets 仍须同步设置并以新 Thread 验证。
- 月台首讲绑定、主动拍摄建议隔离、详情/完成状态隔离、结束总结口径、角色互动预算及 QA/详情的完整自然成文，仍需完成或回归证明。

## 产品决策：先把固定语料写得像人，再用 LLM 做灵活编排

采用“**风格化可变语料库 + 受控知识包 + LLM 完整成文 + 严格发布校验**”。固定语料仍然要继续扩写，但不应再是所有点位通用的句首口头禅；它应成为每种风格可直接发布的高质量保底表达，也是 LLM 的风格示例与措辞素材。LLM 负责根据当前对象、观察目标和上下文灵活选择、组合、改写这些表达，而不是自由编造导览事实。

模型可自由决定：开场角度、观察顺序、段落切分、事实之间的承接、比喻、语气、节奏和收束。模型不得决定：站点、方向、时长、对象身份、工艺名称、数字、传说细节、安全要求、Coverage 或完成状态。

每次生成应使用带 token 的 `KnowledgePack`：模型只编排不可改写事实 token；服务端再还原审核原文，校验 token 完整、有序且唯一，拒绝任何新增事实、后台词、危险互动和超预算文本。语料库提供“像人说话”的下限，模型提供“此时此地怎么说”的变化；两者共同避免模板感，同时保留文化讲解的可靠性。

本轮可适度放宽的是**角色连接语预算**：允许开场、观察动作和转场拥有足够篇幅，避免“抓重点/接着看”式短前缀。不可放宽的是事实 token 完整和顺序、后台词过滤、危险互动、状态写入禁令、总时长预算及失败回退。

## P0：先让测试实例跑到正确链路

1. 在 Streamlit/部署 Secrets 与本地启动说明中同时设置：

```text
PRODUCT_ROLE_NATURAL_DISCOURSE_ENABLED=true
PRODUCT_ROLE_NATURAL_FULL_NARRATION_ENABLED=true
```

2. 初始只灰度四种对照风格：`ancient_scholar`、`bestie_chat`、`buddy_guide`、`exploration_game`；场景覆盖 `route_opening`、`stop_guidance`、`navigation`。
3. 重启 Streamlit 和 LangGraph，并使用新 Thread；旧 Thread 不能用于判断开关是否生效。
4. 每次采样保存运行时配置指纹、`model_called`、`active_takeover`、`fallback_used` 与最终游客文本。没有“模型调用 + Active 发布 + 非 fallback”三项证据的文本，不计入体验验收。

验收：四种风格在同一首站的开场、点位、引路均为真实 Active 输出；关闭任一开关时安全回退，不改变游览状态。

## 模型 API：先做可替换评测，不盲目全站迁移

当前角色成文模型集中在 `agent_graph.py` 的 `_invoke_role_narration_model()`，通过 `ChatDeepSeek` 调用；点位、路线、开场、引路都只接收这个“输入 prompt、返回 JSON 字符串”的窄接口。因此更换**角色成文 API**不是大工程：增加一个 provider adapter、Secrets 配置和统一响应转换即可，知识边界、token 校验、状态提交和 fallback 不应改变。

但不建议先把全站 DeepSeek/RAG/翻译模型一起替换。非 OpenAI 兼容 API 还需处理鉴权、消息格式、JSON 模式、超时/限流、结束原因和内容块格式，测试成本明显增加。

执行顺序：先完成高质量固定语料和双开关验证；再用同一 18 风格 × 7 场景快照，把当前模型与候选 API 做 A/B。只在候选 API 同时提高“风格可辨识、自然度、事实 token 合格率、超时率和单位成本”时，才切换 `ROLE_NARRATION_MODEL` 对应的角色成文 provider。这样可以提升文风，但不会把模型替换误当成语料与产品结构问题的替代方案。

## P0：重构可读段落，而非增加机械缩进

前端不要用首行缩进伪造层级，也不要把服务信息塞进讲解段。后端输出语义段落，前端以段间距、最大行宽和独立服务块呈现；正文无需 Markdown 标题或列表。

```text
角色化开场（1–2 句）

本点观察目标（1 句：此刻要看哪里、为什么值得看）

事实单元 A：工艺或空间（2–4 句）

事实单元 B：当前对象与可见细节（2–4 句）

传说/补充（仅审核内容存在且与当前对象相关时，单独 2–4 句）

本点收束（1 句）

完成/下一站/拍摄建议（独立服务区；按触发条件出现）
```

实施项：

- 将 `NarrationContentPlan` 扩展为带 `section_kind`、`paragraph_id`、`stop_id` 的事实组，而不是把所有事实压成连续正文。
- 更新完整自然叙事协议，让模型输出 `opening`、`paragraph_bridges`、`closing` 及 token 编排；服务端决定段落边界与服务尾。
- 保持 `narration_validation.py` 的“单个空行允许”规则，同时新增：至少三段正文、每段单一语义、服务尾不得并入正文、不得有连续三空行/Markdown/后台字段。
- 保留工作区中 `compose_stop_presentation()` 的双换行变更，并补充 Streamlit 视觉回归，确保 `\n\n` 被真正渲染成段落。

验收：月台与前院中部样本都至少有三段正文；完成/导航/拍摄信息独立显示；没有“审核关联、可核验证据、项目编辑、未核验”等词。

## P0：让风格成为整段叙事，而不是句首口头禅

为每个风格定义“叙事操作”而不只定义词库：

| 风格 | 叙事操作 | 禁止退化 |
|---|---|---|
| 兄弟搭子 | 明确同行关系；用“先看哪里、再怎么辨认”的直接观察路线；偶有简短确认 | 重复“抓重点/接着看/按安排走” |
| 闺蜜唠嗑 | 分享式发现与轻微惊喜；邀请注意一个可见细节，不假装亲密 | 网络梗、过度私密称呼、每段同一句式 |
| 探秘闯关 | 把观察设计成线索推进：先找位置，再认造型，再揭示来由 | 虚构任务、倒计时、未审核剧情或奖励 |
| 古风书生 | 从构件到意涵层层递进，节奏从容，收束有余味 | 堆砌古文、牺牲清晰度 |

实现项：

- 重写并扩展 `point_narration_components_v1.yaml`：每个风格按开场、观察动作、对象辨认、工艺转场、传说引入、本点收束、下一站引路等意图分别提供 8–15 条可替换表达；每条语料必须口语自然、无后台词、无事实断言，并带适用场景/对象类型标签。
- 扩展 `StyleBrief` 的叙事动作、节奏、禁用陈词与句式多样性约束；语料选择须参考当前场景、对象类型和最近已用句，不能随机抽取或循环复用。
- 在同一 Thread 保存最近开场、桥接、收束的规范化表达；生成提示要求避开这些表达，服务端以重复 n-gram/句子检测做一次重试，再失败回退到风格化确定性短文。
- 在模型提示中提供少量与当前风格匹配的优质语料作为措辞参考，并明确要求“先写本点独特的观察动作，再给风格语气”；禁止用空泛过渡句填充段落。
- 为首站、月台、下一站各提供至少两个审核事实组，防止任何风格都只能围绕同一句泛化事实打转。

验收：同一知识包连续生成 5 次，开场/桥接/收束不能复用同一句；四种对照风格的盲读可明显区分；所有事实 token 仍完整且无新增事实。

## P1：补齐状态与场景闭环

1. 月台设为固定端到端回归样本：路线承诺、`stop_id`、对象、工艺、必讲事实、候选、最终文本必须一致。
2. 详情仅重讲当前点：不写 Coverage、不出现完成/下一站/主动拍摄；直接完成、详情后完成、多次详情后完成必须得到等价的下一站首讲与 Coverage。
3. 拍摄建议仅在审核适用点、路线到站且首次讲解时出现；独立服务段，不出现内部过程文本。
4. 路线开场、引路、结束、QA 和改线逐场景迁移到同一完整成文协议；不要继续维护“固定前缀 + 旧正文”的平行体验。
5. 静听模式与不允许互动的角色，路线上不得出现任务、提问、拍照要求或互动时长。

## 测试与发布顺序

1. 先补单元测试：段落规则、token 顺序/唯一性、重复表达重试、服务尾隔离、开关双门、风格禁用语。
2. 再跑状态回归：月台绑定、详情隔离、Coverage、结束总结、拍摄触发、静听模式。
3. 生成 `18 风格 × 7 场景` 的游客端文本快照（路线、开场、首站、月台、详情、引路、结束）。
4. 人工只阅读最终游客端：角色感、自然性、可读性、当前点准确性；失败时再查看 Trace。
5. 四种对照风格通过后，以小比例扩展至其余 14 种；每批均保留 kill switch 和确定性 fallback。

当前已提供四种对照风格的第一轮点位快照工具：`tools/capture_role_narration_snapshots.py`。它会保存古风书生、闺蜜唠嗑、兄弟搭子、探秘闯关在空间/工艺/对象三类审核事实上的最终游客文本、Active/fallback 状态和校验结果。运行前必须显式开启两个自然成文开关；之后以相同输入、不同 `--provider-label` 保存候选 API 结果，才能进行公平 A/B 对比。

## 完成定义

以下同时满足才可关闭本整改：

- 18 风格、7 场景均有新 Thread 自动快照与关键 Trace 证据；
- 四种对照风格在相同知识包下可被稳定区分，且 5 次采样无模板复读；
- 月台和首站至少三段清晰正文，服务信息独立，不泄露后台术语；
- 无事实漂移、无状态污染、无互动合同违例；
- 全量自动化回归通过，并附 Streamlit 视觉截图验收。
