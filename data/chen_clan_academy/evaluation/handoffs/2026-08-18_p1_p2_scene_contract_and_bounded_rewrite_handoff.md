## 3. 当前根因与禁止误改项

### 3.1 已确认的 `opening[0]` 冲突

至少有两处现行代码必须处理：

1. `agent_graph.py` 的成功到达事件，会读取 `brief.point_narration_components["opening"][0]` 并前置到到达提示。
2. `narration_rendering.py` 的确定性兼容路径，会读取同一个点位 `opening[0]` 并加入节点正文。

这会使同一句“眼光看过来、抓重点”等话同时出现在到达确认、全馆开场或节点正文，造成机械拼接和场景错位。P1 必须删除这种跨场景复用；不能只是换一个数组下标或再扩充同一数组。

### 3.2 普通问答的过渡实现不是终点

`qa_role_shadow.py::apply_qa_role_scaffold` 当前把候选重新收敛为 `legacy_public_message`，已经避免普通问答突然出现导览口头禅；但 `agent_graph.py` 仍会执行 QA 角色候选生成与验证。P1 的最终目标是普通 QA 默认不进入角色表演生成链，直接发布已经通过事实和公共安全检查的答案。

### 3.3 不得回退或削弱的边界

- 不得把“审核”等内部术语从公共禁词中移除来解决误拦截。
- 不得让摄影候选查询先于安全识别。
- 不得让 LLM 决定危险动作是否可以执行。
- 不得恢复 `【工艺背景】`、`【观察对象】`、`【观察提示】` 等字段筐。
- 不得修改点位 JSON 来掩盖场景路由或文本组装错误。
- 不得把旧的整段中性正文当作“风格化”，仅在前后拼一句角色口头禅。
- 不得以单元测试通过替代 Streamlit 连续多节点验收。

## 4. P1：重建场景化风格层

### 4.1 架构原则

每个公共响应在生成前必须拥有明确的 `public_scene_kind`。场景合同决定允许的信息、语言形式、生成方式和验证器。不得由一个通用 `opening` 列表跨场景分发。

建议建立一个明确的场景枚举和合同注册表，例如：

```text
arrival_confirmation
route_opening
stop_guidance
navigation
tour_qa
safety_refusal
tour_closing
```

每份合同至少声明：

- 允许输入的数据；
- 必须表达的语义；
- 禁止表达的语义；
- 是否允许使用选定角色风格；
- 是否允许调用 LLM；
- 对应验证器与安全回退。

### 4.2 六个核心场景的无歧义合同

#### A. 到达确认 `arrival_confirmation`

- 只表达两件事：已到达的点位名称、现在立即开始本点讲解。
- 必须是一句简短完整句；不得加入观察动作、故事、工艺定义、路线开场或角色口头禅。
- 可按角色调整称呼或语气，但不得改变上述两项语义，也不得使用节点正文 `opening`。
- 到达成功后必须在同一轮流程继续进入本点正文；确认句不能取代正文。
- 推荐中性基线：`你已到达{display_name}，现在开始本点讲解。`
- 公开消息的 `public_scene_kind` 必须是 `arrival_confirmation`，不能继续标为泛化的 `assistant`。

#### B. 全馆开场 `route_opening`

- 使用专门的路线开场生成器和专属语料/StyleBrief 字段。
- 只介绍陈家祠整体、路线主题、游览方式和第一站衔接。
- 可以体现所选风格，但不得借用节点正文首句，不得提前讲第一件文物的完整故事。
- 首次路线开场只播放一次；重播必须由明确用户意图触发。

#### C. 节点正文 `stop_guidance`

- 负责现场观察、事实讲解、位置与造型辨认、故事组织和自然收束。
- 这是角色风格的主要承载场景。
- 所有可讲解节点都必须到达即讲解，首节点和后续节点使用同一正文合同。
- 首节点可以在路线开场之后接正文，但正文不能因开场已播放而缩短或丢失对象。
- P1 阶段先保证场景隔离与完整事实；P2 才开放事实重组权限。

#### D. 导航 `navigation`

- 只表达下一站名称、方向/路径、预计步行信息和必要现场提醒。
- 不讲当前点或下一点的长篇故事，不使用节点观察开场，不输出路线总介绍。
- 风格只能影响语气和节奏，不能修改方向、顺序、距离或时间。

#### E. 普通问答 `tour_qa`

- 默认直接回答问题，不套当前导览角色的开场、桥接、收束或口头禅。
- 事实检索、证据门、动态信息提示和公共安全边界保持原样。
- 不得出现“眼光看过来、抓重点、这一处先看到这儿”等节点讲解语句。
- QA 只有在未来存在明确、独立且通过验收的 QA 风格合同时才允许风格化；本轮 P1 不做。

#### F. 安全拒绝 `safety_refusal`

- 安全判断必须在点位解析、候选查询、角色生成和普通问答之前完成。
- 输出清楚、克制、直接，并提供安全替代行为；不角色扮演，不开玩笑，不弱化禁止项。
- 明确危险直接拒绝；疑似危险但对象不清时安全澄清。
- LLM 不参与安全结论，也不能把拒绝改写成许可。

### 4.3 P1 推荐修改顺序

1. 新建场景枚举/合同结构及单元测试，不改变现有事实来源和状态机。
2. 给所有游客消息标注准确的 `public_scene_kind`，补齐 `arrival_confirmation` 与 `safety_refusal`。
3. 删除 `agent_graph.py` 到达事件对点位 `opening[0]` 的直接拼接，改走到达合同。
4. 将路线开场迁移到专用生成器，确保不读取点位 `opening`。
5. 将 `narration_rendering.py` 的兼容开场改为 `stop_guidance` 专属组件接口；禁止裸取数组第一项。
6. 普通 QA 路由绕过角色表演生成/提交；保留只读审计可以，但审计不得改变公开答案。
7. 导航与安全拒绝分别接入各自验证器，禁止落回通用角色开场。
8. 先跑 P1 定向测试，再跑全量测试，最后用全新 Streamlit 会话做连续多节点人工验收。

### 4.5 P1 必须新增或保留的验收

1. 到达确认仅一句，包含真实点位与“立即开始”，不含任一节点 `opening` 语料。

8. 18 种风格逐一覆盖节点正文；其他场景按各自合同验收，不能用“出现风格关键词”作为唯一标准。

## 5. P2：给 LLM 有边界的真正改写权

### 5.1 P2 的目标与现状差异

当前模型主要生成 opening、bridges、closing，审核事实由服务端按原句插入。这只能产生“连接语风格化”，无法达到兄弟搭子范本所要求的完整口语叙事。

P2 必须让模型看到本轮允许使用的完整事实，但只允许在事实边界内重组表达。

### 5.2 模型允许做的事情

- 调整审核事实的呈现顺序，但不得跨对象错误归属。
- 把书面事实改写成口语表达。
- 将长故事拆成多个短段和自然停顿。
- 把位置、造型特征与现场观察动作自然组合。
- 在不改变事实含义的前提下合并重复或紧密相关的句子。
- 根据 `stop_guidance` 的 StyleBrief 持续体现角色，而不是只在首句放一个称呼。

### 5.3 模型绝对不能做的事情

- 新增事实库之外的实体、人物、事件、用途、寓意、位置、颜色、材料、年代或数字。
- 修改专名、数字、年代、位置和否定/限制条件。
- 删除任一 `required` 事实。
- 把一个对象的事实移到另一个对象名下。
- 输出内部字段、来源编号、审核状态、文件路径或 Markdown 字段筐。
- 改写、解释或放宽安全规则。
- 修改路线状态、Coverage、到达状态或任何业务状态。

### 5.4 推荐的 P2 输入与输出合同

不要再只把事实隐藏为 opaque slot。建议给模型结构化事实单元：

```json
{
  "scene_kind": "stop_guidance",
  "style_id": "buddy_guide",
  "fact_units": [
    {
      "fact_id": "...",
      "subject_id": "...",
      "subject_name": "...",
      "topic_kind": "craft|location|visual|story",
      "statement": "完整审核事实",
      "required": true,
      "protected_anchors": ["专名", "数字/年代", "位置"]
    }
  ],
  "must_not_claim": ["..."],
  "style_brief": {}
}
```

模型输出不得只给一段无法追溯的全文。建议输出：

```json
{
  "schema_version": "bounded_stop_narration_v1",
  "style_id": "buddy_guide",
  "blocks": [
    {
      "block_id": "block:001",
      "source_fact_ids": ["fact:001", "fact:002"],
      "text": "游客可读文本"
    }
  ],
  "coverage": [
    {"fact_id": "fact:001", "block_ids": ["block:001"]}
  ],
  "self_check": {
    "added_new_facts": false,
    "preserved_protected_anchors": true,
    "covered_all_required_facts": true
  }
}
```

`source_fact_ids` 和 `coverage` 必须由服务端验证，不能只相信模型自报。

### 5.5 P2 硬验证顺序

候选发布前按固定顺序验证：

1. JSON/schema、style_id、block_id 和 fact_id 合法。
2. 每个引用的 fact_id 都属于本次输入；不得跨点位或跨对象。
3. 每条 `required` 事实至少被一个 block 覆盖，不得遗漏或重复计费。
4. 专名、数字、年代、位置及否定限制等保护锚点保持一致。
5. 不得出现事实库之外的新实体或新的事实性断言。
6. 公共消息边界通过；不得出现内部术语、路径、ID 或字段筐。
7. 风格合同、节奏、字符/时长预算通过。
8. 安全类内容不进入本生成器；若意外出现安全语义，候选直接拒绝。

验证失败时，必须回退到“完整、中性、游客可读”的确定性事实讲解。回退不能只剩工艺定义，不能丢文物对象、位置、造型或故事事实，也不能回退到机械的内部错误提示。

### 5.6 P2 推荐实施阶段

1. **Shadow**：模型看到事实并生成结构化候选，但公开文本仍用现有完整中性正文；记录覆盖和差异。
2. **Read-only Active 小样本**：只开放 `stop_guidance`，先测 `buddy_guide`、`neutral`、`child`、`ancient_scholar` 四个差异明显风格。
3. **12/54 样本快照**：要求模型可用、断言为零、无整篇 fallback，并人工检查事实顺序和自然度。
4. **18 风格扩展**：逐风格验证持续性，不只检查关键词。
5. **Streamlit 连续全节点**：首节点、后续节点、详情、完成、下一站均检查；旧会话必须清空后再验收。

### 5.7 P2 必测用例

- 同一组事实允许不同合法顺序，输出都能通过覆盖验证。
- 长故事被拆段但人物、事件、结果和年代不变。
- 位置与造型能合并成自然观察句，保护锚点不丢。
- 删除一个 required fact 必须拒绝。
- 修改专名、数字、年代或位置必须拒绝。
- 引入新人物、新寓意或新地点必须拒绝。
- 把 A 对象事实归给 B 对象必须拒绝。
- 模型超时、无效 JSON、截断、越界或风格不合格时，回退仍完整覆盖全部必需事实。
- 所有安全拒绝测试必须证明 LLM 未被调用。
